# fnlrc · 飞牛音乐歌词补完器

> **fnlrc-next** — 本项目 fork 自 [`Hermannmayer/fnlrc`](https://github.com/Hermannmayer/fnlrc)（MIT），
> 在此基础上独立演进。上游原版权与许可声明见 [LICENSE](LICENSE)。

给[飞牛 OS（fnOS）](https://www.fnnas.com/)的音乐库补歌词。

具体点说：你库里那些日语歌、英语歌、俄语歌，歌词只有原文看不懂，或者干脆没歌词——这个工具把它们补成「原文 + 中文翻译」的格式，写到音频文件旁边，让飞牛音乐显示成双行。

不需要显卡，不需要填 API key，打开就能用。

---

## 它到底会做什么

你选一个音乐库文件夹，点开始，然后：

1. **把这个文件夹扫一遍**，读每首歌的标签（标题、艺人、专辑、时长、语言），看它现在有没有 `.lrc` 文件、那个文件是不是乱码。
2. **需要处理的歌，去网上找歌词**。主力是网易云，找不到就用 LRCLIB 兜底。网易云上大部分日语、英语、俄语歌都带现成的中文翻译，而且是人工或字幕组做的，质量比机器翻的好。
3. **没有翻译的，才去补翻译**。源站已经给了翻译就用它的，一个字都不动；只有源站漏掉的那些行，才会送去翻（这一步默认关着，见下面「翻译后端」）。
4. **合成成双行格式**。飞牛的双行显示不是靠什么特殊标签，就是「同一时间戳出现两行，被归为一组一起高亮」。所以译文行必须和原文行用**完全一样的时间戳**，差 10 毫秒都不行。合成完之后，程序会用飞牛前端的规则自己先检查一遍，确认写出去确实会双行，不然就不写（或者退一步写单语）。
5. **写到音频旁边**，同名 `.lrc`，UTF-8 编码。要覆盖已有文件的话，先备份成 `.lrc.bak`。

全程默认是「预览模式」——只把结果生成到一个单独的目录给你看，不碰你的音乐库。确认没问题了再取消勾选，真写进去。

### 它会怎么处理你现有的文件

这是最要紧的一张表。**它不会无脑覆盖你的东西**：

| 你现在的情况 | 它会怎么做 |
|---|---|
| 文件夹里没有 `.lrc` | 去网上找，找到就写一份新的 |
| 有 `.lrc`，但是乱码或者空文件 | 重新找一份。找不到就原文件不动（见下） |
| 有 `.lrc`，已经是合规的双语 | **跳过，一个字都不改** |
| 有 `.lrc`，是中文单语 | 跳过（中文歌不需要翻译） |
| 有 `.lrc`，是外文单语（日语、英语……） | **保留你文件里的时间轴和断句**，只把译文按相同时间戳插进去（见下） |
| 音频文件里内嵌了歌词 | 照样处理，但飞牛读的是内嵌那一版，外挂文件会被压住（见「风险」第 5 条） |
| `language` 标签是 `zxx`（纯音乐） | 跳过，一次网络请求都不发 |
| 文件名带「伴奏 / 纯音乐 / karaoke」，而且网上也找不到 | 跳过 |

### 关于「乱码」

乱码文件会被重刮。但要先给你打个预防针：**重刮多半救不回来**。

因为乱码往往不是这一份文件的问题，是**源头就坏了** —— 真实见到过的一种是：GBK 编码的中文被按 Big5 解码，再存成 UTF-8。这种文件表面上是合法 UTF-8、也能正常打开，只是里面的字全是错的（"看着像中文，其实是别的字"）。重刮回来的还是同一个坏源头。

所以程序会把乱码的**形态**写进报告（例如 `mojibake:gbk-as-big5`），而不是笼统说一句"重来过"。看到这种提示，正确的做法是：

- 找到这首歌的正确原文，手工放一份 `.lrc` 进去；
- 或者干脆让它保持单语/无歌词 —— 比挂一份乱码强。

### 关于「你已经有一份外文单语歌词」

这是最容易被误解的一条，单说。

以前的做法是**整份重抓**：网上找到什么就用什么，你本地那份的时间轴、断句、自己加的标注全没了。对「时间轴是自己一句一句对过」的人来说，这是净损失。

现在的做法是**保留本地时间轴**：解析你已有的 `.lrc`，把网上找到的译文**按相同的时间戳**插进去，原文行一个字都不动，时间戳也一个都不改。配对逻辑是：

1. 先按时间戳就近配（±0.9 秒内），优先配有译文的那条候选；
2. 时间戳对不上时，按**原文文本的相似度**配（两边时间轴来源不同时，行数和时刻常常对不齐，只能看词）；
3. 都配不上就留空 —— 宁可不补，也不乱配。

如果这样拼出来的结果过不了飞牛的双行规则（译文覆盖太少），程序会**自动退回重抓**，并在报告里写明原因。

**不想要这个行为**：网页版设置里有「外文单语歌词：保留本地时间轴，只把译文插进去」这个勾选框，取消即可；命令行加 `--rebuild-local`。

> 两点边界：本地文件已经是**双行**的时候不会走这条路（那种情况下它就是"已是合规双语"，该跳过就跳过）；`--force` 会强制重做，那一次也会改用源站的时间轴。

## ⚠️ 用之前，先看这一条

**飞牛不会重新读已入库歌曲的 `.lrc`。**

飞牛把 `.lrc` 当成「第一次解析这首歌时读一次」的输入，读完就存进它自己的数据库了。之后你再怎么写文件它都不会再看一眼——扫描、改文件时间、重写文件、甚至把文件移出去再移回来，都试过，无效。

这不是这个工具的 bug，是飞牛的设计。但它直接决定了你该怎么用。

**要给新歌补歌词，正确顺序是：**

```
下载 → 先放进一个暂存文件夹（不在飞牛音乐库里）
     → 用 fnlrc 处理这个暂存文件夹
     → 处理完再把歌整个移进音乐库
```

这样 `.lrc` 和音频文件是一起被飞牛第一次看到的，它自然会读。

**歌已经在库里了怎么办**，没有轻松的办法。三条路，代价都写在 [docs/FNOS-SIDECAR.md](docs/FNOS-SIDECAR.md) 里：

- 用它自己的歌词功能（飞牛的界面里没做这个入口，走不通）
- 改它的歌词数据库（能保住歌单，但要动另一个应用的数据库，工具里带了这个功能）
- 把音乐库删掉重新加一遍（界面就能做，必然有效，但所有歌单、收藏、播放历史会失效）

完整实测记录在 [docs/TECH-NOTES.md](docs/TECH-NOTES.md) 的 2.3 节。

> **不想碰命令行？** 如果你服务器上部署了 AI 助手（Hermes、Claude Code 之类），
> 把 [docs/AGENT-RUNBOOK.md](docs/AGENT-RUNBOOK.md) 交给它，让它照着做。
> 那份是专门写给 AI 看的：每一步该跑什么命令、输出应该长什么样、失败怎么办，都写死了。

## 怎么装、怎么跑

### 桌面版（Windows）

适合不想碰命令行的。双击运行，选文件夹，点开始。

怎么拿到、怎么自己打包、首次运行会遇到什么，看 **[docs/GUIDE-DESKTOP.md](docs/GUIDE-DESKTOP.md)**。

### 网页版 / NAS（Docker）

适合想把工具跑在 NAS 上的人——直接读写本地路径，绕开 SMB 和 WebDAV 的权限问题。

```bash
docker build -t fnlrc .
docker run -d --name fnlrc -p 127.0.0.1:8080:8080 \
  -v /vol2/1000/音乐:/music \
  -v fnlrc-data:/data \
  fnlrc
docker logs fnlrc 2>&1 | grep -i token     # 拿到访问令牌
```

浏览器打开 `http://<NAS-IP>:8080`，第一次会让你填那个令牌。

部署细节、令牌怎么管、权限怎么调、怎么把结果回填到飞牛数据库，看 **[docs/GUIDE-WEB.md](docs/GUIDE-WEB.md)**。

### 命令行

```bash
# 只看现状，不联网不写文件
python -m fnlrc scan --root "/vol2/1000/音乐"

# 预览（默认就是预览，只生成到 fnlrc_out/）
python -m fnlrc run --root "/vol2/1000/音乐" --limit 20 --report report.json

# 真写进去
python -m fnlrc run --root "/vol2/1000/音乐" --write

# 起网页版 / 看配置 / 重置令牌 / 探测飞牛歌词库
python -m fnlrc --server --open
python -m fnlrc config
python -m fnlrc token --rotate
python -m fnlrc fnos --app-data /usr/local/apps/@appdata/trim.music --appmeta /vol2/@appmeta/trim.music
```

`run` 的退出码：`0` 全部正常，`1` 用法或致命错误，`2` 跑完了但有失败项。方便放进 cron。

命令行输出默认是中文。想换成英文，加 `--lang en`（放在子命令前面）：

```bash
python -m fnlrc --lang en scan --root /music
FNLRC_LANG=en python -m fnlrc scan --root /music      # 环境变量，一次设置一直有效
python -m fnlrc config --set lang=en                  # 写进配置，长期生效
```

优先级：`--lang` > 环境变量 `FNLRC_LANG` > 配置项 `lang` > 中文。网页端不看这几项，它认的是设置面板里那个下拉框。

### 翻译后端

默认是「源站译词」：只用网易云自带的中文翻译，**一次后端请求都不发**，完全不往外发歌词（找歌词本身要联网，那是另一回事）。源站没给翻译就写单语。

如果你遇到源站翻译覆盖不全的歌，可以配一个自己的大模型 API 来补翻漏掉的行：

```bash
python -m fnlrc config --set remote_base_url=https://api.deepseek.com \
                       --set remote_model=deepseek-flash \
                       --set remote_api_key=sk-xxxx
python -m fnlrc run --root 音乐 --write --translate remote
```

只支持 DeepSeek 一家，因为它够便宜。Base URL 填 `https://api.deepseek.com`（**不要加 `/v1`**，官方文档给的就是不带 `/v1` 的），模型名填 `deepseek-flash`（另一个可选值是 `deepseek-v4-pro`）。

协议是 OpenAI 兼容的，所以自建的 vLLM、one-api、LM Studio 也能填进来，把 Base URL 指到那个端点就行。

**用了这个后端，歌词文本会发给 DeepSeek。** 不想出网就别配它。

## 风险

按「会不会真的出事」排序。

### 1. 已入库的歌补了也没用

上面说过，再强调一次：这是最容易让人以为「工具坏了」的一条。工具本身工作正常，文件也写对了，只是飞牛不看。

判断方法：补完之后在飞牛里点扫描，如果歌词没变，就是这个问题，不是工具的问题。

### 2. 匹配到的歌词可能是另一首歌

同名不同版本太多了。实测搜一首「告白の夜」能返回 16 个候选，时长从 60 秒铺到 303 秒，里面有钢琴版、翻唱版、Remix、中文填词版。

程序做了四道拦截，按强度递增：

- **标题清洗**：剥掉 `_hires`、`(Short Size)`、`【192kHz 24bit】`、`- Remastered 2011` 这类后缀再搜。只剥已知清单里的，`Bella ciao (啊朋友再见)` 这种合法括号标题不会被误伤。
- **版本标记降权**：候选标题里带了原曲名没有的 `Live`、`翻唱`、`伴奏`、`Remix` → 扣分。
- **时长硬闸**：这首歌和候选的时长差超过 10 秒 → 直接淘汰。Live 版和加长版跟录音室版的时长差普遍远超 10 秒，只扣分挡不住。
- **语言校验**：外文歌却抓到中文歌词 → **不写**，丢进「待人工确认」让你自己看。

**但做不到 100%。** 时长、艺人、标题全对但是另一首歌的情况理论上存在。

降低风险的办法：报告页有一列叫「匹配到」，写的是它实际配到了哪一首（`艺人 - 歌名`）和打分。跑完扫一眼这列，有不对的马上能看出来。另外「待人工确认」那一栏永远排在最上面。

### 3. 会覆盖你现有的 `.lrc`

只有「外文单语」会被覆盖，而且是先备份成 `.lrc.bak` 再写。但如果那首歌你以前处理过、`.bak` 早就存在了，程序**不会**用新的覆盖旧的 `.bak`——也就是说 `.bak` 里是最早那一版。

想撤回：把 `.lrc.bak` 改回 `.lrc` 就行。

### 4. 机器翻译会翻错

如果你开了「我的 API」，漏掉的行会交给大模型翻。日常歌词够用，但句式绕的、有双关或典故的句子容易翻反。

源站（网易云）的翻译是人做的，质量更好——所以程序优先用它，机器只补它漏掉的行。正式场合建议人工过一遍。

### 5. 内嵌歌词永远盖住外挂文件

飞牛的读取优先级是 `内嵌 > 外挂 .lrc > 在线刮削`。

所以如果某首歌的音频文件里内嵌了歌词，你写多少遍外挂 `.lrc` 都没用。预览页会检测这种情况并告诉你，但**工具不提供清除内嵌的功能**——那要改写音频文件，风险高，得单独设计。

### 6. 网页版部署的安全问题

- **令牌就是钥匙**。网页版跑在 NAS 上，任何能访问那个端口的人，都能触发扫描和**写入**你的音乐库。令牌在启动日志里，怀疑泄露就 `fnlrc token --rotate` 重置。
- **默认只监听回环**（`127.0.0.1`）。要局域网访问得自己改成 `8080:8080`，那就必须靠令牌保护。
- **绑 127.0.0.1 不等于安全**。你机器上任何进程、以及任何能访问 `http://127.0.0.1:<端口>` 的网页，都能发请求。所以写操作一律要令牌 + 同源校验。
- **API key 本身不会泄露**。它只存在服务端（环境变量优先，否则 `config.json`），浏览器拿不到回显，页面上只能看到「已配置」和一个打码的值。

### 7. 改飞牛数据库的风险（只在你用那个功能时）

`fnlrc fnos` 会直接改飞牛音乐应用的数据库。它能保住歌单（因为只改歌词正文、保留 `lyric_id`），但：

- 要能访问飞牛的**两个**应用私有目录，通常要 root：主库在系统盘
  `/usr/local/apps/@appdata/trim.music/`，歌词正文在存储池 `/vol2/@appmeta/trim.music/`
  —— 它们在两个文件系统上，容器要挂两处，只挂一处探测就会报「没找到」
- 歌词正文在分片的 `lyric_content` 表里，主库的 `lyric` 表**只是索引**（没有正文）
- 默认**不给"一行歌词都没有"的歌建行**（那会往它的库里插记录）。
  要用得显式开 `--allow-insert`（网页版设置里也有勾选框）。
  真机实测这条路可行，能补上原本完全填不了的那批歌
- 飞牛升级一次改了表结构，它就会失效——程序会先探测结构，对不上就**拒绝执行**，不会硬写
- 每次都自动备份，但你自己再手动备份一次不亏

细节在 [docs/GUIDE-WEB.md](docs/GUIDE-WEB.md) 和 [docs/FNOS-SIDECAR.md](docs/FNOS-SIDECAR.md)。

### 8. 第三方接口随时会变

网易云和 LRCLIB 都是非官方接口，没有承诺。已经真实发生过一次：2026 年 9 月，网易云的搜索路由 `/api/search/get/web` 被停用了，返回 HTTP 200 但内容是「操作频繁」、结果为空。不修的话主源等于全废。

程序做了降级：一个源挂了就换下一个，不会整体失败。但如果两个源同时变，这个工具就得跟着改。

### 9. 版权

只处理你自己库里的歌，抓公开歌词、合成、写到你自己的硬盘上。不内嵌、不托管、不分发任何歌词数据。歌词版权归原作者和版权方。

## 出问题了怎么办

**先跑这个，它会把整条决策链打印出来：**

```bash
python scripts/debug_song.py --file "/path/to/某首歌.flac" --preview 12
```

它会告诉你：读到的标签是什么、预期语言是什么、网易云返回了哪些候选、每个候选打了多少分、为什么选中了这一个、语言校验过没过、最后生成了什么、飞牛规则校验结果是什么。一首歌没配上或者配错了，跑这一条基本就能定位。

**其他常用工具：**

```bash
python scripts/scan_library.py --root /path/to/音乐        # 库概览，不联网
python scripts/probe_write.py  --root /path/to/音乐        # 测试目录能不能写
python scripts/smoke_sources.py                            # 测试数据源通不通、延迟多少
```

**几个常见现象：**

| 现象 | 原因 |
|---|---|
| 补完飞牛里没变化 | 正常。飞牛不重读已入库歌的 `.lrc`，见风险第 1 条 |
| 大量「无歌词」 | 歌太冷门，或者文件名太脏，或者 LRCLIB 在墙外连不上 |
| 大量「超时」 | 网络慢，或者被限流了。把单曲超时调大试试 |
| 歌词只有原文没有翻译 | 源站没给翻译，而你没开翻译后端 |
| 歌词是单语而不是双语 | 源站翻译只覆盖了一部分行，成对比例不够 80%，过不了飞牛的双行规则，所以退回单语，而不是什么都不写 |
