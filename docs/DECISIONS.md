# 关键决策记录（ADR）

> 记录「为什么这么做」，避免后来人（包括未来的自己）把有意的设计当成待修的缺陷。

---

## ADR-001：一套代码三端复用，不用 Electron / Tauri

**决策**：核心用 Python，UI 用 FastAPI + 单页前端，桌面端用 `pywebview` 包一层原生窗口；网页端就是同一套服务容器化。

**理由**
- 业务逻辑（飞牛规则、源抓取、翻译、写入）天然适合 Python，且已有验证过的实现
- 用户要求「桌面 GUI」+「能网页部署」——若用 Electron/Tauri，等于**维护两套 UI 载体 + 两套打包链路**（JS 壳 + Python 核心）
- 「Web UI + 原生窗口壳」让两者**共用同一份前端**，桌面版还能拿到原生文件夹对话框

**代价**：桌面版体积比 Tauri 大（约 60–120MB）；依赖系统 WebView2（Win10+ 一般自带）。

**否决方案**：Electron（体积/双运行时）；Tauri（需 Rust 侧车 + Python 打包，复杂度反而更高）；纯 Qt/PySide6（UI 无法复用给网页版，违背「网页部署」需求）。

## ADR-002：默认「源站自带译词」，而不是调用翻译后端

**决策**：默认 `translate="source"` —— 只用网易云自带的 `tlyric` 译词，**不调用任何翻译后端**。
用自己的 API 是显式的可选增强。

**理由**
- 用户明确要求「让没有大模型的人也能开箱即用」——不能把任何前置条件挂在默认路径上
- 实测：日语/英语/俄语的抽样歌曲**全部自带中文译词**，且来自人工/字幕组，质量优于机器翻译
- 零成本、零配置、**零出网**：默认路径下歌词文本不离开本机

**代价**：覆盖面取决于源站；冷门曲可能没有译词 → 此时降级为「写单语 + 标注」，而不是报错。

## ADR-003：只对**缺译文的那几行**调用后端，拿不到就写单语

**决策**：后端只在源站没给出译文的行上工作；整首拿不到译文时产出**可用的单语文件**并在报告里标注
（`written_mono`），绝不什么都不写。

**理由**
- 用户的核心痛点是「原语言单行 + 刮错 + 乱码」，**双语是增强而非唯一目标**
- 源站译词是人工/字幕组做的，比机器翻译好 —— 能复用的就别重翻
- 宁可写单语（至少修正了乱码和格式），也不要因为「翻不出来」而什么都不做

**实现注意**：单语文件必须**绕过** `validate()`。校验器对单语恒为 `False`
（`paired_groups` 数的是"有 ≥2 行的时间戳"），让它参与校验会把无译文的歌判成"两个候选都不通过"，
反而一个文件都不写。见 `docs/TECH-NOTES.md` 1.3。

## ADR-004：可疑匹配绝不自动写

**决策**：外文曲目抓到中文版歌词（`lang_mismatch`）等情况，**不写文件**，进人工确认队列。

**理由**
- 实测真实发生：俄语歌匹配到中文翻唱版（标题、时长都对得上，但歌词是中文的）
- 写进去会让时间轴错乱，用户还以为工具搞坏了库 → 信任成本极高
- 只影响极少数歌，人工确认的代价远低于「默默写错」

## ADR-005：串行处理 + 全局节流，而不是并发

**决策**：v0.1 单任务串行，且对每个源设最小请求间隔（网易云 0.35s、LRCLIB 1.2s）。

**理由**
- 第三方是**非官方接口**，高并发=被限流/封禁风险，代价远大于收益
- 串行 8.9s/首，520 首 75 分钟——对「一次性补库」完全可接受
- 节流是**降低 429 最有效的一招**（实测：并发打源反而让单曲耗时从 8s 涨到 90s）

**后续**：若真要并发，必须共享同一个节流器，且对 LRCLIB 保持串行。

## ADR-006：单曲 25 秒总时限 + 源级快速失败

**决策**：每个源有独立超时（LRCLIB 8s，网易云 20s），整首歌有 25s 总时限，超时记 `timeout` 状态供下轮重试。

**理由**：真实事故——LRCLIB 偶发 20–35s 慢响应，配合重试把单曲拖到 **89.9 秒**，直接让整轮跑不动。修复后同一首歌 5.1 秒。
**教训**：**批量任务里，「慢」比「失败」更致命**——失败是逐首隔离的，慢会拖垮整批。

## ADR-007：写入前备份 `.lrc.bak`，且不覆盖合规文件

**决策**：① 替换已有 `.lrc` 前备份为 `.lrc.bak`；② 已是「合规双语」或「中文单语」的文件默认跳过；③ 提供回滚。

**理由**
- 用户的音乐库是**不可再生资产**，工具的第一义务是不破坏它
- 「跳过已合规文件」让工具可以**反复运行**（每天 cron 只处理新歌），适合日常使用

---

## ADR-008：默认「预览模式」不落盘

**决策**：UI 首次使用时默认勾选预览（输出到 `fnlrc_out/`），确认后再写入。

**理由**：面向非技术用户，「先看会发生什么」是降低误操作恐惧的最有效手段；同时它也是排错利器（把生成的文件直接发给开发者看）。

---

## ADR-009：语言判定必须「假名优先」

**决策**：`detect_lang()` 先查假名/谚文，再判汉字占比。

**理由**：这是真实 bug——日语歌因汉字比例高被判成中文，导致**整库日语歌都没能生成双语**。顺序错了，功能等于不存在。

## ADR-010：`language=zxx` 作为纯音乐的权威判据

**决策**：优先用标签 `language=zxx` 判定纯音乐并跳过；目录名/文件名关键词只作兜底。

**理由**：实测 520 首里有 53 首带 `zxx`（"no linguistic content"），是标准字段，比猜文件名可靠得多；能省下大量无意义的网络请求。

---

## ADR-011：v0.1 用 JSON 存储，而不是直接上 SQLite

**决策**：先用 `manifest.json` + `report.json`，v0.2 再换 SQLite。

**理由**：JSON 可人读、可 diff、可直接贴到 issue 里排错；MVP 阶段「可观测」比「可查询」更重要。存储层做了接口隔离，替换成本可控。

---

## ADR-012：只写外挂 `.lrc`，不改音频文件

**决策**：v0.1 不写内嵌歌词（不做音频标签改写），但会**检测并提示**内嵌歌词的存在。

**理由**：改写音频文件是**不可逆的高风险操作**（不同格式的标签结构差异大、可能损坏文件）。而「检测+提示+让用户决定」已能解决 90% 的问题（用户可自行用其他工具清除）。

## ADR-013：文档优先写「实测数据」，不写推测

**决策**：`TECH-NOTES.md` 里的每条结论都必须标注实测来源（延迟数字、覆盖率、失败案例）。

**理由**：这个项目的难度不在代码，而在**第三方行为的不确定性**（接口字段、限流、慢响应、编码）。把实测数据写下来，后来人才能判断「我的失败是环境不同还是代码坏了」。

## ADR-014：移除本地模型（Ollama）后端

**决策**：不再支持 `translate="local"`。后端只剩「源站译词」（默认）和「用户自己的
OpenAI 兼容端点（DeepSeek）」。

**理由**
- 它对**默认体验**没有任何贡献：要用户先装 Ollama、拉模型、占显存，而它的收益只是
  "省一点 API 费用"——但默认路径本来就不花钱（源站译词）
- 4B 级别的小模型翻译质量明显不如源站的人工译词，FAQ 里也只能诚实地写"会翻错惯用语"
- 维护成本全在边界上：模型缺失、冷启动、显存不足、容器里 `localhost` 指向自己、
  思考模式吃光输出预算……每一条都要单独处理，而它们只服务于一条可选路径
- 想完全不出网的用户，用默认的 `source` 就够了

**代价**：完全没有外网、又要补翻冷门曲的用户少了一条路。他们的替代方案是自己起一个
OpenAI 兼容端点（self-host 的 one-api / vLLM 都行）再填进「我的 API」。

**否决过的折中**：保留 `local` 但默认关闭。这仍然要维护上面那一整串边界，
而"默认关闭的功能"实际使用率极低 —— 删掉更诚实。

## ADR-015：承认「旁挂歌词只在首次入库时被读取」，把产品的默认工作流反转为「先补完、再入库」

**背景**：实测推翻了本项目早期版本的核心假设。旧文档写的是"写完 `.lrc` 后在飞牛里点一次扫描就生效"，
**这是错的**。已入库的路径永远不会被重新解析（扫描 / mtime / 重写 / 移出移回全部无效，6 种方式实测）。
完整实测矩阵见 `docs/TECH-NOTES.md` 2.3。

**决策**

1. **不再承诺"写完点扫描就生效"**。所有面向用户的文案、CLI 输出、UI 提示都必须说清楚这一点。
2. **默认工作流反转**：`新歌 → 暂存目录补完 → 移进音乐库`。这是唯一零风险、零 DB 操作的路径。
3. **对已入库的歌，如实列出三条出路与代价**，不假装有一条"轻松解决"的路：
   - 删库重扫：界面可做、必然有效，但所有 `track.guid` 变化 → 歌单/收藏/播放历史/歌词偏好全失效
   - 改它的歌词库（原地写歌词正文、保留原 `lyric_id`）：歌单全保，但要碰另一个应用的数据库（**两处**：主库在系统盘、歌词正文在存储池 —— 见 ADR-017）
   - 在新歌上补：等价于删库重扫
4. **不把"改它的数据库"做成默认行为**。那是高权限、跨应用、依赖对方表结构的操作，
   飞牛一次升级就可能失效 —— 它只能是显式开启的高级功能，且必须自带备份与版本探测。

**为什么值得单独记一条**：这不是一个 bug 修复，而是**产品定位的修正**。
原项目的价值主张是"给已入库的歌补上双语歌词"，而平台的机制决定了这条路对存量歌没有零成本解。
把这件事说清楚，比给用户一个"点了没反应"的工具更重要。

**未决**：飞牛自带的歌词链路（`lyricDownload` 任务 / `auto_download_lyric` / `source=4 手动关联`）
是否接受本地文件、能否保住 guid —— 未实测。若成立，它会是存量歌最佳的出路（纯界面操作、零 DB 风险）。

## ADR-016：本地已有的外文单语歌词**当基线**，而不是重抓覆盖

**背景**：`decide()` 一直把「外文单语歌词」标成 `bilingualize`（"外文单语歌词 → 补成双语"），
但 `bilingualize` 全仓库**零消费者** —— 实际走的是联网重抓、整份覆盖。
界面上承诺的行为一直没有代码去做。用户指出这个落差时，顺手把一个更严重的问题带出来了：

**对有精修过时间轴的用户，整份覆盖是净损失。** 他们花时间对齐的轴、自己加的断句，
重抓一次就全没了；而重抓回来的译文往往只是在原轴上换了个来源。

**决策**：新增 `Config.keep_local`（默认 **开**）。外文单语歌词的曲目：

1. 解析本地 `.lrc`，**沿用它的时间轴与断句**
2. 把抓来的译文用 `providers.align_translation()` 对到**本地的毫秒**上
3. 对齐顺序：时间戳就近（±900ms，同刻有原文行和罗马音行时**优先挑带译文的**）
   → 原文文本相似度兜底（`min_text_sim=0.62`，刻意偏高）→ 配不上就留 `None`
4. 结果过不了飞牛双行规则 → **自动退回重抓**，并把原因写进 `note`
5. 报告里是独立状态 `written_keep_local`

**为什么默认开**

- 最坏情况等于关掉它：对齐不满意的会自动退回重抓，不会产出比现在更差的东西
- 它符合用户对 `bilingualize` 那个标签的**既有预期**（标签本来就是这么写的）
- 反过来说：默认关掉就等于默认"用户的轴可以被覆盖"，而这是不可逆的（虽有 `.bak`）

**为什么"配不上就留空"而不是"按顺序硬配"**

两边的断句常常不同（本地两句并一行、源站拆两行，或反过来）。按顺序配会把译文**整段错位**，
错位后的双语比单语更难看 —— 配错一行的代价远大于少配一行。

**边界（刻意不做的情况）**

- 本地文件**已经是双行**（同一时间戳出现两行）→ 不走这条路。那种情况属于"已是合规双语"，
  该跳过就跳过；`--force` 重做时更不能拿它当基底，否则会把原文行和译文行同时当成"本地原文"
- 本地文件**是中文单语** → 本来就无需双语
- 本地行数 < 4 → 成对规则本来就过不了，别浪费一次对齐

**为什么给独立状态而不是并进 `written`**：两者在文件位置、歌单影响上没有差别，
但在**用户可见的后果**上有差别 —— 前者原文行与时间戳一个都没动。需要能一眼分辨。

**未决**：`--force` 会覆盖被保住的轴（强制重做 = 整份重来）。目前只在文档里说明，
没做"force 也保留本地轴"的选项 —— 那会让 `--force` 的语义变得含糊。

## ADR-017：飞牛的数据在**两处**、在两个文件系统上、分**两张表**

**背景**：本项目早期版本以为"一个 data-dir 里能找到全部"，据此写的探测在真机上直接判
「结构与预期不符」。2026-09-15 真机核实后确认：**飞牛没改表结构**，是路径预期错了。

```
/usr/local/apps/@appdata/trim.music/db/music.db      主库（系统盘 /，ext4）
    audio_file(id, path, …)   track(id, guid, audio_file_id, …)
    lyric(id, guid, track_id, source, stored_guid, created_at, updated_at)   ← 索引，不含正文
    user_track_lyric_preference(user_id, track_id, lyric_id, …)
/vol2/@appmeta/trim.music/lyric-sqlite/lyric-<NN>.db 歌词分片，16 个（存储池 /vol2，btrfs）
    lyric_content(guid PK, content BLOB, created_at)     ← 正文在这里
```

**关联链是三段，缺一不可**：
`audio_file.id` ← `track.audio_file_id`；`track.id` ← `lyric.track_id`；
`lyric.stored_guid` → 分片文件 → `lyric_content.guid`。

补充事实：`/vol2/@appdata` 里**没有** `trim.music`；分片名是
`"lyric-%02x.db" % int(stored_guid[0], 16)`，**两位零填充**（真机 660/660 命中）；
**全库没有 `isLRC` 列**。

**决策**

1. **两处路径是一等参数**，不是一个"data-dir"。`fnos.py` 用 `--app-data` / `--appmeta`
   （旧参数 `--data-dir` 保留兼容）；探测报告**两行独立打勾**，只挂一处时一眼能看出是哪一处。
2. **探测报告必须回显真机上的表名与列名**。判"结构不符"时那两行就是证据本身，
   操作者不必再猜一轮 —— 这是对"路径预期错位"那次误判的直接补救。
3. **分片文件名两位零填充**：`"lyric-%02x.db" % int(stored_guid[0], 16)`。
   漏掉零填充会把 `bc8…` 算成 `lyric-b.db` 而真机上是 `lyric-0b.db` —— 真机第一次统计时错过 660 条。
4. **正文表是 `lyric_content`，不是 `lyric`。** 而**全库没有 `isLRC` 列**，写库时不要试图设它。

**这三条是同一类错误**：本项目早期版本把"正文放在主库的 `lyric` 表、还有个 `isLRC` 列"
当成了事实，而那张表结构**真机上根本不存在**。测试夹具也是照它编的 —— 所以测试全绿，
脚本在真机上必然报「结构与预期不符」。
**教训**：夹具必须照真机的表结构造，否则测试给的是一份虚假的安全感。

### 关于"新建 `lyric` 行"（2026-09-15 受控实测后修正）

**原决策"不新建 `lyric` 行"只在一种情况下成立** —— 该曲**已经有**歌词行。
理由是 `user_track_lyric_preference` 以 `lyric_id` 为键，新增一行而不同步偏好，
偏好仍指向旧行。真机实测验证了这一点：版本数变成 2，但 `preferred` 没变，**用户看不到新版本**。

对「库里一行都没有」的歌（真机 520 首里 142 首，约四分之一），实测结论是**可以建行**：

| 场景 | 做法 | 结果 |
|---|---|---|
| 该曲没有任何歌词记录 | `INSERT lyric(source=2, stored_guid=…)` + INSERT 分片正文 | ✅ 应用立即认；**不用碰偏好表** |
| 该曲已有歌词，再插一条 | 只 INSERT | ⚠️ `preferred` 仍是旧那条 |
| 同上，补上偏好 | upsert `user_track_lyric_preference(user_id, track_id, lyric_id)` | ✅ 立即切换 |

**修正后的决策**：
- 已有歌词的歌 → **原地 UPDATE**（首选：还能保住 `user_track_lyric_offset` 里的歌词偏移）
- 没有歌词的歌 → **INSERT**（安全），但要 `--allow-insert` 显式开启 —— 它会往另一个应用的库里插记录
- 多版本共存 → 本工具**不做**。它要求同时 upsert 偏好表，收益不明确而风险实打实
- `source` 写 **2**（同目录旁挂），不写 3 —— 内容确实来自旁挂 `.lrc`

**否决过的折中**：让 `fnos.py` 自动探测并两处都试。飞牛只挂一处时探测会报"没找到"，
比"猜一处然后用错的路径写"安全 —— 猜错会写进另一个应用的库。

## ADR-018：首次使用走一步「引导」，而不是裸弹令牌框

**背景**：网页版第一次打开时直接弹一个令牌输入框。对全新环境来说这是**两道门叠在一起**：
先要弄懂这个框是什么，再要去找令牌从哪来，然后还得自己摸到第一屏去填音乐库路径 ——
而这三件事本该有人带一步。用户（C1）提出：首次登录 / 无配置 / 配置损坏时应有引导。

**决策**

1. **首次使用显示三步引导**：`欢迎 → 填访问令牌 → 选音乐库`，而不是裸弹框。
2. **「全新环境」的判据由服务端给**（`store.setup_needed()`），前端只读 `setup_needed` 布尔：
   - 标记过 `setup_done` → 不需要（永不打扰）
   - 配置文件**损坏** → 需要（多半被手工改坏，重走一遍顺便自动修复）
   - **从没扫描过任何库**（无 `last_root`）→ 需要
   - 其余 → 不需要，直接进主界面
3. **回环访问时省掉「令牌」这一步**：服务端已把令牌注进页面，让本机用户填自己根本
   不需要的令牌是纯添乱。非回环（局域网 / 容器）才要用户手填。
4. **令牌校验走一个只读、无副作用的新端点 `/api/auth`**，校验口径与写操作完全一致
   （令牌 + 同源）。不拿一个写接口（如 `POST /api/config`）去试错 —— 那会在验证失败时
   留下半个副作用。
5. **「跳过引导」= 这次不引导**，不写 `setup_done`（下次打开仍会出现）；
   **「完成」才记 `setup_done`**。这样"手滑点了跳过"和"我真的不需要引导"是两回事。
6. **不破坏既有令牌机制**：`require_token` / `X-FNLRC-Token` / 回环注入一律照旧。
   引导结束后仍会调用原来的 `initGate()` —— 没拿到令牌就弹原来的闸门兜底。

**为什么 `setup_needed` 由服务端判、而不是前端自己拼条件**：前端要自己判断就得同时知道
"有没有配置文件""它坏没坏""扫过库没"，等于把服务端的持久层逻辑复制一份到浏览器里，
两处一旦漂移就会各自为政。判定只放一处（`store.py`），前端只消费一个布尔值。

**为什么用 `last_root` 而不是"有没有 config.json"当「老用户」判据**：很多用户会为了改一个
设置项（比如勾上备份）先打开设置面板存一次 —— 那也会生成 config.json，但他其实**从没跑过**。
用"扫过库没"才是真正走完主流程的信号。

**未决**：引导目前只覆盖"首次进门"。M1 的监听目录、M2 的 provider 配置等新设置项，
是各自在设置页里给提示，还是也纳入引导，留到对应阶段再定。

## ADR-019：监听文件夹用「纯轮询」，并且永远不动没查到的歌

**背景**：M1「监听文件夹」—— 盯着一个目录，新歌下进来就自动补完。核心风险是**误动文件**：
下载器正在写半截文件、临时文件、以及查不到歌词的歌。这类错误一旦发生就是数据丢失，
无法靠"用户注意点"规避。

**决策**

1. **纯轮询，不引入 watchdog**。每 `poll_s` 秒扫一遍目录，比对 大小+mtime。理由：
   - 跨平台一致。inotify（Linux）在飞牛的容器里未必可用，SMB/CIFS 挂载上的
     文件系统事件支持参差不齐 —— 而监听目录**恰恰最可能在 SMB 上**。
   - 零新依赖。核心依赖只有 `requests` + `mutagen`，不为一个后台功能再拉一个原生扩展。
   - 轮询的"笨"在这里反而是优点：状态是**拉出来的**，不是**推过来的**，
     中间丢了一个事件也不会卡死，下一轮自然补上。
2. **静默期（`quiet_s`）**：一个文件要连续两轮观察**大小+mtime 都不变**才认为"写完了"。
   半截文件（0 字节 → 逐渐变大）在变化期间会被无限期推迟。默认 8 秒。
3. **临时后缀直接忽略**：`.part` `.tmp` `.crdownload` `.!ut` `.aria2` 等（`TEMP_SUFFIX`）。
   下载器的中间文件连候选都不是。
4. **"缺词件"原地不动**（`no_lyrics` / `timeout`）：查到歌词**之前**不搬、不删源文件。
   搬走一个还没补完的歌，等于永久失去它的"原始位置"这个重试线索。
   只有真正处理出结果了（`written*` / `dumped` / `skipped_existing`）才搬运。
5. **重试是有限、退避的**：`no_lyrics` 等可重试状态记 `attempts`，按
   `RETRY_DELAYS = (60, 300, 1800)` 秒退避，`MAX_RETRY = 3` 次后放弃。
   简单的瞬时故障（还没刮到词）会自愈，持续失败不会无限打源站。
6. **搬运先复制、成功后再删源**（copy-then-delete）：`place()` 先 `copy2` 到目标，
   成功了才 `os.remove` 源。跨盘（比如从 SMB 到本地）时移动失败会**留下源文件**，
   而不是"删了源、目标没写成"。
7. **撞名规则：新的上位，旧的退 `.bak`**。目标已有同名时，把旧文件重命名成
   `<name>.bak`，新文件用回原名。若 `.bak` 已被占用，则退成 `<name> (1).ext.bak`
   （`_retire_candidates` 逐个试），**绝不覆盖任何已有备份**。
8. **状态落盘（`watch-state.json`）**：记录每个已处理文件的 大小+mtime+状态。
   重启后已处理且未变化的文件不会重跑；变了（mtime/大小）则视为新内容重跑。
   写盘用 `os.replace` 原子替换，中途崩溃不会留下半个 JSON。
9. **默认只预览、不写**：`watch_write` 默认跟随全局，但面板上给的是显式勾选；
   `dry_run` 模式连 `watch-state.json` 都不落盘（纯观察，零副作用）。
10. **配置读取口径统一**：`POST /api/watch/start` **读已保存的配置**，不接受请求体。
    面板上「开始监听」会先把输入框的值存一次再 start —— 避免"界面显示 A、
    实际用 B"的分裂。校验（目录存在、搬运目标存在、两者不同）也在 start 时做。

**为什么"缺词件"不搬** —— 这是本 ADR 最容易被质疑的一条。直觉是"处理完了就搬走"，
但 `no_lyrics` 不是"处理完了"，是"这次没查到、以后可能查得到"。文件留在原地，
退避重试就能碰到它；搬到音乐库则要反过来去库里找，还可能被飞牛当成正式入库歌
（旁挂歌词对已入库歌无效，见 ADR 相关条目）。

**未决**：目前是单目录（`watch_root`）监听。多目录、目录级不同策略（一个目录 move、
另一个 keep）留到后续再定。是否用 watchdog 作为"轮询的加速器"（有事件就早扫一轮、
无事件就按 poll_s）也留待观察真实开销后再定。


## ADR-020：歌词源用「协议 + 注册表」，官方源与社区插件同一套接口

**背景**：M2「provider 插件化」—— 目标是「新增一个歌词源 = 新增一个文件，不改核心」。
现状是 `providers.py` 一个文件约 800 行，把凭据脱敏、节流、打分、网易云、LRCLIB、
翻译后端全塞在一起，加一个新源必须动核心文件、还得理解全部内部细节。

**决策**

1. **`Protocol` 而不是基类**。插件只需鸭子类型地提供 `name/label/priority/needs_key/
   available()/fetch()`，**不必 import 本项目的基类**。`@runtime_checkable` 让我们
   能在启动自检时 `isinstance(x, Provider)`。降低耦合，社区复制模板即可。
2. **两类外部能力分清楚**：
   - **歌词源（Provider）** → 产出 `pairs`，走本协议；
   - **翻译后端（Translator）** → 已有 `translate` 配置（源站译词 / DeepSeek），**不动**。
   本 ADR 只重构"源"，翻译后端保持现状。
3. **官方源也是插件**。内置源放 `fnlrc/providers/builtin/`，用**同一个协议**注册，
   走**同一条降级链**。这样"官方路径"和"插件路径"不是两套代码，插件作者看到的接口
   就是官方自己每天在用的接口。
4. **注册表 + 编排层**。`registry.register()` 收源（同名默认不覆盖，插件不会静默顶掉
   内置源）；`fetch_lyrics()` 按 `priority` 升序依次问每个可用源，第一个给出可用结果的
   即采用。`pipeline` 只认 `fetch_lyrics`，不再认识具体某个源。
5. **失败隔离，但"全炸"要如实上报**。单个源 `available()` 或 `fetch()` 抛异常 → 记日志、
   继续下一个源（一个坏插件不能拖垮整首歌）。但若**所有可用源都抛了异常**、最终没有结果，
   `fetch_lyrics` 会把异常经 `errors` 参数带回，`pipeline` 据此报成 `error` 而不是
   `no_lyrics` —— 否则一个持续崩溃的源会被当成"这首歌没歌词"，用户永远等不到它自愈。
6. **值约定**：`pairs` 是 `(毫秒, 原词, 译文|None, 罗马音|None)`；**没有译文用 `None`
   不用空串**（上层靠 `is None` 判断"缺哪几行要送去翻译"）。毫秒严格递增、无重复。
7. **插件不做沙箱**（Python 插件信任本地用户），但加载时**打印来源路径**，
   并在 `provider list` 里显示每个源的可用性与原因。
8. **约束（安全重构）**：测试里大量 `monkeypatch.setattr(P, "netease_fetch", …)` 直接
   打桩顶层函数，因此实现**必须继续能从 `providers` 顶层命名空间访问**。做法：把
   `providers.py` 降级为 `providers/` 包，旧函数全部留在 `__init__.py`；内置适配器用
   **函数体内的 `from .. import netease_fetch`**（延迟取属性）调用它们，这样打桩依然生效。
   这不是洁癖，是"迁移期间保持 322 个既有测试全绿"的唯一低成本路径。

**取舍记录**：曾考虑直接把 `netease_fetch` 等整体搬进 `builtin/` 并让测试改打桩点，
那样更"干净"，但要同时改动 6 个测试文件、且会破坏"旧函数名做薄包装"的向后兼容承诺。
选择"顶层保留实现 + builtin 薄适配"换取了零破坏迁移。

## ADR-021：人工翻译是「一等公民」——导出/导回 + 网页逐行编辑

**背景**：默认路径是「源站译词」，覆盖不到冷门曲时只能写单语（`written_mono`）；
远端机器翻译又会翻错惯用语与专有名词。对追求质量的用户，**人工翻译是唯一能保证
质量的路径**。此前工具完全没有支持它的入口，用户只能自己手工改 `.lrc`。

**决策**

1. **人工翻译与 `source` / `remote` 并列**，是第三种模式，而不是一个外挂脚本。
   CLI 新增两条命令 `translate-export` / `translate-import`，网页新增逐行编辑器，
   两者**共用同一个 `fnlrc/manual.py`**，行为一致（验收标准第 5 条）。
2. **导出的文件是"待译清单"，不是整份歌词**。只收「缺译文的那几行」，连同
   `index`（行序号）与 `time` 一起给。CSV 给人（Excel），JSON 给工具。
3. **CSV 用 `utf-8-sig` 写出**。这是验收标准第 1 条 —— 不加 BOM，Excel 打开中文就是乱码，
   功能等于不可用。
4. **导回走"校验链"，不过就拒绝对应行、绝不静默**：
   - 行数与 `index` 连续、无重复；
   - `original` 与现有歌词逐字一致 —— 防「导出后源站数据变了导致错位」；
   - 译文非空 → 参与合成；空行 → 保持原文单语。
   校验不过时**一个字节都不写**（宁可不动，也不半写）。
5. **时间轴一个都不动**。合成是把译文按**相同时间戳**插进去（复用
   `build_bilingual_roles` + `validate`），而不是联网重抓、整份覆盖 —— 与 ADR-016
   的 `keep_local` 同源思路。验收标准第 4 条钉死这一点。
6. **网页编辑的四个决策**（对齐 `plan/DECISIONS-CONFIRMED.md` C1–C4）：
   - **C1 读接口不校验令牌，写接口必须**。`/api/manual/lines` 返回的就是用户自己库里的
     歌词文本，读它没有风险；`/api/manual/save` 落盘，与其它写操作同级，必须持写令牌。
   - **C2 显式点「保存」**，不自动保存；未保存内容先存浏览器 `localStorage` 草稿，
     防误关丢失。保存成功才清草稿。
   - **C3 记忆库做，默认关**。勾选后才把本次译文写进
     `$FNLRC_DATA/translation-memory.json`，供跨歌复用。
   - **C4 上下文开关，默认关**。CLI 导出的 `--context` 附带前后各一行原文。
7. **记忆库只记「非中文 → 中文」方向**。原文已是中文、或译文不是中文，都不记 ——
   避免跨语种误用（这是"错误译文被到处复用"的主要风险来源）。
8. **路径用 `/` 归一化**（`_portable`）。Windows 导出的 CSV 拿到 Linux 上导回也要能对上，
   不能让 `\` 与 `/` 的差异把行匹配搞丢。

**取舍记录**
- 曾考虑网页"边编辑边保存"，那样省事但会误改；选择**显式保存 + 本地草稿**，
  用一点操作成本换「不会手滑毁掉原文件」。
- 曾考虑网页编辑器里也给上下文列，但**整首歌的歌词本来就铺在眼前**（逐行列表），
  直接看上一行即可，再单独给一列上下文是冗余。
- 导回**不新建歌词行**：人工翻译只补「已有时间轴、缺译文」的歌；连 `.lrc` 都没有的歌
  应先去抓一份单语再补译，不在这一步凭空造时间轴。

**未决**
1. 多首歌一次性导回时的错误定位 —— 目前按 `file` 分组报问题，行号标注待补。
2. 记忆库复用是否要「打个招呼」（提示"这句用了记忆库译文，请核对"）—— 倾向要，待做。
3. 网页编辑器是否支持搜索/跳转长歌词 —— 长歌可能上百行，待评估是否需要。

**未决**
1. 首批新源：本轮只迁移现有两源（网易云 / LRCLIB）+ 打通插件框架。QQ/酷狗需 cookie /
   加密签名、接口易失效，Musixmatch 需 key 且商用受限 —— 留作独立插件，等明确需要再做。
2. 多源**串行降级**（本 ADR）还是并发——倾向串行（沿用 ADR-005），可后加"并发只读源"开关。
3. 源偏好学习（某首歌 A 源更准就记住）——倾向不做。
4. `providers_enabled` / `provider_keys` 目前只支持配置文件 + CLI；是否要完整 UI 配置页待定。
