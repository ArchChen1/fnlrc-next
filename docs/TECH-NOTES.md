# 技术笔记（实测数据与踩坑记录）

> 本文是整个项目的技术地基：所有结论都来自**在真实音乐库（520 首）上的实测**，不是推测。
> 如果你要改这个项目，先读这一篇。

---

## 一、飞牛音乐的双行显示机制

### 1.1 机制

飞牛音乐前端内置一个 LRC 解析器，其中有一个显式机制：**同一时间戳出现多行时，这些行会被打上同一个 `parallelGroupId`，作为一组一起高亮、一起滚动**。这就是「原文 + 译文」双行显示的底层实现——**不是**靠自定义标签，也不是靠两行不同时间戳，而是**严格同一时间戳**。

推论：
- 译文行必须使用**与原文完全相同**的时间戳（`[00:17.63]` 对 `[00:17.63]`），差 10ms 都不成组。
- 想要双行，就必须**整首成对**，只翻副歌几句的写法会被降级成「译文只是下一条歌词」。

### 1.2 硬规则（从解析器逻辑抽出，做了边界实测）

| 规则 | 阈值 | 说明 |
|---|---|---|
| ① 至少成对 | **≥ 4 组** | 只有 3 对 → 不识别为双行 |
| ② 成对比例 | **≥ 80%** | 从第一对开始算：成对数 / 总时间戳数 |
| ③ 前奏单语 | **≤ 8 行** | 开头允许少量单语行（如纯音乐前奏、念白） |
| ④ 不得混用逐字标签 | 互斥 | 出现 `<mm:ss.xx>` 逐字卡拉OK标签时走「逐字着色」显示，双行失效 |

### 1.3 边界实测用例（回归测试必须覆盖）

| 写法 | 实测结果 |
|---|---|
| 每行原文紧跟一行同时间戳译文（交错） | ✅ 并行组 4 |
| 原文整段在前、译文整段在后（分段） | ✅ 并行组 4 |
| 5 行前奏单语 + 之后 5 组成对 | ✅ 并行组 **5**（曾误记为 10 —— 那是行数，不是组数；`paired_groups` 数的是"有 ≥2 行的时间戳"） |
| 20 对 + 尾部 3 行单语 | ✅ 并行组 20 |
| 前 10 对 + 后面 20 行单语 | ❌ 不识别（成对比例不足） |
| 只有 3 对 | ❌ 不识别（< 4 对） |
| 逐字卡拉OK `<mm:ss.xx>` | ✅ 但走另一种显示（逐字着色），与双行互斥 |
| **单语文件**（只有原词一行一个时间戳） | ❌ `ok=False` —— **`validate()` 对单语永远是 False** |

> 实现见 `fnlrc/lrc.py::validate()`，返回 `paired_groups / leading_mono / pair_ratio / karaoke_tags / ok`。

⚠️ **最后一行是个陷阱**：`paired_groups` 数的是"有 ≥2 行非空的时间戳"，单语文件这里是 0，
所以 `ok` 恒为 `False`。单语文件之所以能正常写出去，是因为 `pipeline.py` 里那条分支
**直接返回、绕过了校验**。任何"构造两种产物、都跑 `validate()`、取通过的那个"的写法都会
把"无译文"的歌变成"两个候选都不通过" → 一个文件都不写。**单语必须被显式声明为永远可接受，
不能让它走 `validate()`。**


### 1.4 LRC 格式支持范围

- 时间戳：`[mm:ss.xx]`（标准）、`[mm:ss:xx]`、`[mm:ss]`、以及全角括号 `［］`
- 表头：`[ti:]` `[ar:]` `[al:]` `[by:]` `[offset:±ms]` 等均可识别
- 编码：UTF-8 最稳（服务端能转 GBK/Big5/UTF-16，但库里实测有被转坏的，见第四节）

---

### 1.5 行角色与输出策略

网易云一次返回三个字段，但**什么该写进文件**是另一回事。每一行都要先定角色：

| 角色 | 来源 | 默认是否写进 `.lrc` |
|---|---|---|
| `orig` 原文 | `lrc.lyric`（去掉混排的罗马音之后） | ✅ |
| `trans` 译文 | `tlyric.lyric` 中**判为中文**的那一条 | ✅ |
| `roman` 罗马音 | `romalrc.lyric`；或 `lrc` 里混排的拉丁行；或 `tlyric` 里其实是音译的那条 | ❌ 默认不写 |

**默认只输出「原文 + 译文」两行**（`lrc.build_bilingual_roles(roles=("orig","trans"))`）。
罗马音默认不落盘 —— 三行同时出现会让飞牛把同一时间戳的三行归成一组，用户要的是双行。

判定难在两处，都踩过：

1. **`lrc` 里混排罗马音**。两种形态都要认：与原文**对齐**（同/±300ms 时间戳）是强信号；
   **交替出现**（原文一行、罗马音一行、时间戳顺序递增）是弱信号，**要求至少 2 行**才认 ——
   否则副歌里孤零零一个 `Yeah` 会被当成罗马音摘掉。证据不足时一律不拆，宁可漏拆。
2. **`tlyric` 里混着罗马音**。原文非拉丁、候选是纯拉丁 → 判为罗马音，不占译文行。
   注意**不能靠字符重合判断**：罗马音与假名/汉字没有共同字符。
   另外要先剔掉"与原文完全相同"的候选 —— 有些上传把原文再抄一遍，不剔的话英文歌会
   因为"英文更长"而选中原文自己。

## 二、文件约定与优先级

### 2.1 位置与命名

```
音乐/日语/24.Violet Snow (Short Size).wav
音乐/日语/24.Violet Snow (Short Size).lrc   ← 同目录、同主名、换扩展名
```

### 2.2 读取优先级（实测代码逻辑）

```
内置歌词(4)  >  外挂 .lrc(3)  >  在线刮削/下载(1)
```

优先级本身成立，但**只在"首次解析这个音频路径"时被评估一次**（见 2.3）。
所以下面两条推论都带条件：

1. 给「只在线刮到错歌词」的歌写外挂 `.lrc` → 盖过在线那版 ✅ ——**前提是这首歌还没入库**
2. 给「音频内嵌了歌词」的歌写外挂 `.lrc` → 会被内嵌压住 ❌ 必须先清掉内嵌歌词

### 2.3 ⚠️ 生效时机：飞牛**不会**重新读你写的 `.lrc`（2026-09 实测推翻旧结论）

> **这一节推翻了本项目早期版本的核心假设。** 旧版写的是"写完文件后在飞牛里点一次扫描就生效"，
> 那是**错的**，会把用户引到一条死路上。

**机制**：飞牛把旁挂歌词当作**首次解析音频时的一次性输入**，不是可变更的资产。
歌词/封面是在解析音频文件的环节读取的（二进制里的 `scraper/local.lookupSidecarLyrics`）。
索引逻辑是「**路径即身份**」：扫描确实每次都遍历文件系统（实测文件数 519 → 521 → 519 会同步变化），
但对已经在 `audio_file` 表里的路径**一律跳过** —— 不是"比对内容再决定要不要重解析"。

**实测矩阵**（对一首**已入库**的歌改 `.lrc`）：

| 触发手段 | 结果 |
|---|---|
| 音频 + 同名 `.lrc` **一起**首次入库 | ✅ 自动读到（`source=2`，正文=文件原文） |
| 已入库后再放/替换 `.lrc` + 全库重扫 | ❌ |
| `touch` 改 mtime | ❌ |
| 原样重写 `.lrc` / 音频（触发写入事件） | ❌ |
| 改写音频内容/标签（`ffmpeg -c copy`，size 变了） | ❌ 连 DB 里的 size 都不更新 |
| 给音频追加 1 字节 + 全库重扫 | ❌ |
| 移出目录 → 扫描 → 移回 → 扫描 | ❌ 只清"已物理删除"标记 |
| **删掉该曲的记录 → 扫描** | ✅ 重新入库并读到 `.lrc`，**但 GUID 会变** |
| **原地改写正文（保留 `lyric_id`）** | ✅ 立即生效、无需重启、无副作用 |
| 整个库删掉再加回 | ✅（全量版，GUID 全变） |

应用确实带了 inotify 监听（`sharedLibraryFSEventHandler`：`OnFileCreated` / `OnFileCloseWrite` /
`OnFileModified` / `OnFileMoved`…），但它只用来维护"文件存在状态"，**实测对音乐库目录里的写入/移动没有任何反应**。

文件消失时只把记录标记 `is_physical_file_deleted=1`；文件重现时只清掉标记，**不重解析**。
唯一会被解析的是**新路径** —— 那正是读 `.lrc` 的唯一时机。

**结论**：旁挂歌词的变更完全没被纳入 change detection，这是应用的设计缺口。
「先入库、后补歌词」在飞牛上**天生走不通**。

**因此正确的工作流是反过来**：

```
新歌 → 先放到暂存目录（不在飞牛音乐库里）
     → 用 fnlrc 补完歌词（.lrc 与音频同目录）
     → 再把整首移进音乐库     ← 此时 sidecar 与音频一起被首次解析，天然生效
```

对**已经入库**的歌，见专文 [`docs/FNOS-SIDECAR.md`](FNOS-SIDECAR.md) ——
里面有决定树、四条出路的详细做法与代价、以及验证清单。没有零成本的解。

### 2.4 内嵌歌词的优先级

飞牛读的是 `内嵌 > 外挂 .lrc > 在线刮削`（对应 `lyric.source` 的 `1` / `2` / `3`；
`4` 是"用户手动关联"）。所以**音频里内嵌了歌词时，外挂 `.lrc` 永远盖不住它** ——
这是独立于 2.3 的第二道坎：即便你解决了"重新解析"，内嵌歌词仍然优先。
处理办法只有清掉内嵌（改音频标签，本项目不做），或者干脆不折腾这首歌。

### 2.5 数据布局：主库和歌词正文在**两块盘**上（2026-09 真机核实）

> **这一节推翻了本项目早期版本的第二个假设。** 旧版以为"一个 data-dir 里能找到全部"，
> 于是在真机上把主库挂进容器后，探测直接判「结构与预期不符」—— 实际上飞牛根本没改表结构，
> 是探测的**路径预期**错了。

```
/usr/local/apps/@appdata/trim.music/db/music.db    ← 主库：audio_file / track / 偏好表
                                                     系统盘 /（ext4）
/vol2/@appmeta/trim.music/lyric-sqlite/lyric-*.db  ← 歌词正文，16 个分片
                                                     存储池 /vol2（btrfs + trimacl）
```

| 事实 | 细节 |
|---|---|
| 主库别名 | `/var/apps/trim.music/var` → `/usr/local/apps/@appdata/trim.music`（软链，两种写法都行） |
| **`/vol2/@appdata` 里没有 `trim.music`** | 那里只有别的应用（fygo-browser / trim.hermes / WxBackup）。挂那儿必然"没找到 music.db" |
| 主库的 `lyric` 表**只是索引** | `id, guid, track_id, source, stored_guid, created_at, updated_at` —— 没有正文列 |
| 正文在分片的 **`lyric_content`** 表 | `guid PK, content BLOB, created_at`。在主库找正文会直接判"结构不符" |
| **全库没有 `isLRC` 列** | 搜过所有表。别去设它 |
| 两个目录在两个文件系统上 | 所以容器**必须挂两处**，没有单挂的写法 |
| 分片号 | `stored_guid` 的**第一个十六进制字符** → `"lyric-%02x.db" % int(g[0], 16)`，**两位零填充**（`bc8…` → `lyric-0b.db`）。真机 660/660 命中；漏掉零填充会错掉大部分 |
| `lyric.source` | `1`=内嵌、`2`=同目录旁挂、`3`=在线刮削、`4`=用户手动关联 |
| 偏好表 | `user_track_lyric_preference` / `user_track_lyric_offset` 在**主库**里，以 `lyric_id` 为键 |
| 权限 | `@appmeta` 是 `770 root:root`、分片 755/644、`music.db` 644；应用自身以 root 跑（PID 实测 user=root） |

**为什么这条要紧**：偏好表以 `lyric_id` 为键 → **保留 `lyric_id` 就保住了歌单、收藏、
播放历史与歌词偏移**。"删记录重扫"会换掉全部 `guid`，把上面这些一起废掉。
这两条合起来，就是 [`docs/FNOS-SIDECAR.md`](FNOS-SIDECAR.md) 路线 3 的全部依据。

### 2.6 新建歌词行是可行的（2026-09 受控实测）

> **这一节推翻了 ADR-017 当初的保守结论。** "不新建 `lyric` 行"只对"已经有歌词行的歌"成立。

真机受控实测（库内临时目录放副本 → 建行 → 用应用自己的接口验收 → 清理）：

| 场景 | 做法 | 结果 |
|---|---|---|
| 该曲**没有任何**歌词记录 | `INSERT lyric(source=2, stored_guid=…)` + INSERT 分片正文 | ✅ 接口立即认（版本数=1，`source=2`）；**不用碰偏好表** |
| 该曲**已有**歌词，再插一条 | 只 INSERT | ⚠️ 版本数=2，但 `preferred` **仍是旧那条** —— 用户看不到新版本 |
| 同上，补上偏好 | `upsert user_track_lyric_preference(user_id, track_id, lyric_id=新行)` | ✅ 立即切到新行 |

**所以三分法的正确做法**：已有歌词 → 原地 UPDATE（首选，还保住歌词偏移）；没有歌词 →
INSERT（安全）；要多版本共存 → INSERT **且必须** upsert 偏好。

**两条实现细节**：
- `user_id` 从 `user` 表取（真机 `Home=1`、`lian=2`），偏好表唯一键是 `(user_id, track_id)`，用 upsert 不用 insert
- 分片名两位零填充（见上表）—— 真机第一次统计时漏掉，错了 660 条

本工具只做前两种，对已有歌词的歌一律原地更新 —— 从根上避开多版本那个坑。

真机结构指纹（25 张表 + 每张表的列、25 张表里线上独有的 `app_hook`、16 个分片的编号命中统计、
逐项权限/属主）见交付的 `fnOS-音乐-1.0.1-结构指纹.json`。应用版本 1.0.1，未更新过，
线上表/列与应用自带的 `sqlite.sql` + v2 + v3 完全对得上。

## 四、歌词数据源实测

### 4.1 网易云（主力源）

| 项 | 实测值 |
|---|---|
| 搜索延迟 | **0.2–0.3s**（国内直连非常快） |
| 能拿到什么 | 原词（带时间戳）+ **中文译词**(tlyric) + 罗马音(romalrc) |
| 覆盖率 | 抽样日语/英语/俄语歌曲，**全部自带中文译词** |
| 限流 | 低频使用无感；批量时仍建议 ≥0.35s/次 |

返回字段（供实现参考）：
```
lrc.lyric     原词，形如 [00:02.46]残酷な天使のように
tlyric.lyric  中文译词，时间戳与原词对齐
romalrc.lyric 罗马音
```

#### ⚠️ 搜索路由变更（2026-09 实测，必须知道）

`/api/search/get/web` **已停止工作**：HTTP 200，但返回体是
`{"code":405,"msg":"操作频繁，请稍候再试"}`，`result.songs` 为空。

一度以为是自己被限流，但同一秒内 `/api/search/get` 正常返回 5 条结果，
静置 20s 后 `/web` 复测仍是 405 —— **是路由被停用，不是限流**。

| 路由 | 实测结果 |
|---|---|
| `POST /api/search/get` | ✅ 正常，字段齐全（`id` / `name` / `duration`(ms) / `artists[].name`） |
| `POST /api/search/get/web` | ❌ 恒返回 `code:405 操作频繁`，`songs` 为空 |
| `GET /api/song/lyric` | ✅ 正常（`lrc` / `tlyric` / `romalrc` / `klyric` 都在） |

**影响**：不修的话主源等于全废，全库只剩 LRCLIB 兜底，而 LRCLIB 不提供译词
→ 双语功能整体失效。`providers.NE_SEARCH_URLS` 现在按顺序试这两个路由，
第一个返回结果的就采用，所以路由再变时只需改这张表。

**顺带实测**：`/api/song/lyric` 的 `nolyric` 字段只在网易云**明确标记**无歌词时才为
`true`；纯粹的器乐曲（如 Ayasa 的 `告白の夜`，290s）返回的是空字符串 `lrc` 且
`nolyric` 缺失。所以 `nolyric` 只能当加分项，判空仍要靠 `parse_lrc()` 的结果。


**注意**：原词里会混入制作名单行（`[00:00.000] 作词 : 及川眠子`），这些行**必须剔除**——它们是「单语行」，会拉低成对比例，几行就可能把整首踢出双行判定。

### 4.2 匹配打分与消歧

多版本（Live / 翻唱 / 伴奏 / 短版）是误配的主要来源。实测 `告白の夜` 一次搜索就返回
16 个候选，时长从 60s 铺到 303s，只有 `告白の夜 / Ayasa` 290s 是原曲。现有四道处理：

| 手段 | 规则 | 依据 |
|---|---|---|
| **时长硬闸** | 两侧都有时长且差 > **10s** → 候选直接淘汰（不再是扣分） | Live 版/加长版与录音室版的时长差普遍远超 10s，只扣 1.5 分挡不住。任一侧缺时长则不判断 |
| **版本标记降权** | 候选带了原曲名没有的 `live/cover/remix/acoustic/伴奏/カラオケ` 等 → **−2.5** | 单边有标记才扣；原曲名自己带 `live`（库里存的就是 Live 版）或两边同标记时不扣。`remaster` 刻意不在列 —— 重制版唱同一首词，降权会拒掉唯一正确的匹配 |
| **标题清洗** | 剥离 `_hires`/`_H`/`(Short Size)`/`(TV Size)`/`【192kHz 24bit】`/`- Remastered YYYY` 等**已知清单**后缀，作为额外查询式 | **绝不"剥掉所有括号"**：`Bella ciao (啊朋友再见)` 是合法标题。关键词必须带 `\b`，否则 `ver` 会在 `(Cover)` 里匹配到 `Co|ver` |
| **标题相似度** | 包含关系 + 长度惩罚；归一化后 <4 字符必须完全相等（**只对标题**） | 旧的字符集重合率给 `Hello`/`Halo` 打 0.75。短标题规则不能用于艺人：`H△G` 归一化后只有 3 字符，会归零 2.0 的艺人项 |

**语言一致性只加权（+1.5），绝不淘汰候选**。原因见 5.1：目录名与 `language` 标签本身
都可能错，而网易云存在**罗马音版本的 `lrc`**（`detect_lang` 会判成 `latin`）——
按语言淘汰会丢掉正确匹配。唯一的硬闸仍是「外文曲目 + 歌词是中文」。

### 4.3 LRCLIB（欧美曲库补充）

| 项 | 实测值 |
|---|---|
| 正常延迟 | < 1s |
| **异常延迟** | **偶发 20–35s**（实测 `/api/get` 22.6s，首次 search 35.8s） |
| 内容 | 时间轴原词（`syncedLyrics`）/ 纯文本（`plainLyrics`）/ `instrumental` 标记 |

**必须做的工程处理**（这是真实事故换来的）：
- 超时设 **8s 快速失败**（不要用 25s 默认值）
- 重试 **1 次**（不要 4 次——重试会把 35s 放大成 90s）
- **单曲总时限 25s**：超了就记 `timeout` 状态，下一轮再补
- 效果：同一首歌从 **89.9s → 5.1s**

### 4.4 翻译后端（`Config.translate`）

```
网易云（原词 + 现成译词）
   └─ 命中且有译词 ──────────────▶ 直接双语，零成本，质量来自人工/字幕组
   └─ 命中但无译词 ─┐
LRCLIB（时间轴原词） ─┘
                  └─▶ 只对**缺译文的那几行**调用后端
                          └─ 也没有 ──▶ 写单语文件并标注（仍优于现状）
```

| `translate` | 行为 |
|---|---|
| `source`（默认） | **不调任何后端**。源站没给译词就写单语 —— 零配置、零成本、零出网 |
| `none` | 同 source，且明确表示"不翻译" |
| `remote` | 调用户自己配的 DeepSeek 端点补翻缺译文的行 |

只翻**缺译文的那几行**：源站译词优先，它来自人工/字幕组，质量比机器翻译好。
远端返回部分结果时**逐行保留**，翻了一半的行不会被丢回单语。

> 早先还支持过本地模型（Ollama），已下线：它要用户先装模型、占显存、冷启动慢，
> 而覆盖率上的收益远不如"源站译词 + 一个便宜的大模型 API"这条组合。
> 想完全不联网就用默认的 `source`。

### 4.5 远端后端（DeepSeek）

只支持 DeepSeek 一家。Base URL `https://api.deepseek.com`（**不带 `/v1`**）、模型 `deepseek-flash`，
OpenAI 兼容，`remote_translate` 直接复用。

四个必须显式处理的点：

1. **必须显式关掉思考模式**（2026-09 核对官方文档后补的，此前漏了）。
   DeepSeek 的 `thinking.type` **默认是 `enabled`**，且默认强度 `reasoning_effort: high`。
   对翻译这种任务它是纯负担：思考 token 照计费、慢，而且**会吃掉 `max_tokens` 的预算** ——
   我们设了 4096，一旦思考占满，正文就空 → `_parse_numbered` 拿不到 → 90% 门槛不过 →
   **整首降级为单语**。这和它下面那条 `max_tokens` 是同一个失败模式，只是成因更隐蔽。
   顺带：官方文档写明 **`temperature` 在思考模式下不生效**，所以一直发的 `0.1` 也是空设。
   关掉思考后 `temperature` 才真的起作用。

   ```python
   extra = {"thinking": {"type": "disabled"}} if is_deepseek(base_url) else {}
   ```

   **但这是 DeepSeek 专有字段**：换成 one-api / vLLM / LM Studio 时，严格校验的端点会用 400
   拒掉未知字段。所以只在**主机名含 deepseek** 时才发，且万一还是 400 就**去掉它重试一次**
   （`_EXTRA_REJECT` 分支）—— 功能不受影响，只是那台服务器上关不掉思考模式。

2. **必须传 `max_tokens`**。不传走服务端默认值（**未设置时非思考模式默认 8K、思考模式默认 64K**），
   长歌的译文会被截断 → `_parse_numbered` 只拿到一部分 → 90% 门槛不过 → 整首降级为单语。
3. **非 200 要能区分原因**，否则设置页的「测试连接」只能报一句"失败"。实测 DeepSeek：
   `401 → API key 无效`、`402 → 余额不足`、`404 → Base URL/模型名不对`、`429 → 限流`。
4. **凭据类错误不要重试**（400/401/402/403/404）。重试等于白等，直接跳到下一个后端。

> **模型名与 base_url 以官方文档为准**（`https://api-docs.deepseek.com/zh-cn/`）：
> base_url 是 `https://api.deepseek.com`（**不带 `/v1`**；带 `/v1` 实测也能通，但文档给的是不带的），
> 模型只有 `deepseek-flash` 与 `deepseek-v4-pro` 两个。
> 旧的 `deepseek-chat` 已不在文档里 —— 模型名这类东西会变，**别照着记忆写，去查文档**。

**`remote_translate` 只翻缺译文的行**，所以选了 DeepSeek 也仍然依赖网易云/LRCLIB 提供
原词与时间轴 —— key 留在服务端并不减少第三方元数据流量。

## 五、语言判定：一定要「假名优先」

**踩过的坑**：最初用「CJK 字符占比 > 阈值」判断是不是中文。结果**日语歌被判定为中文**——因为日语大量使用汉字，且假名（`\u3040-\u30ff`）也被算进 CJK 范围。后果是整首日语歌被当成中文，**只写了单语文件，双语功能对日语完全失效**。

**正确判定顺序**（`fnlrc/lrc.py::detect_lang()`）：

```python
1. 出现假名（\u3040-\u30ff）        → "ja"   # 必须最先判
2. 出现谚文（\uac00-\ud7af）        → "ko"
3. 汉字占比 > 50%                   → "zh"
4. 西里尔占比 > 30%                 → "ru"
5. 拉丁字母占比 > 50%               → "latin"
6. 其他                             → "other"
```

### 5.1 交叉校验：外文歌却抓到中文版歌词

**踩过的坑**：一首俄语歌（`Russian Chorus - 莫斯科郊外的晚上`），两个源都只找到**中文翻唱版**歌词（`关牧村`、`姚璎格` 的版本）——标题、时长都对得上，但歌词是中文的，时间轴与俄语演唱未必对齐。

**对策**：
- 用「曲目预期语言」（来自 `language` 标签，缺失时用目录名兜底）与「歌词实际语言」比对
- 判定规则要**松紧合适**：
  - ❌ 太严：「预期 ru，歌词 zh」一律拦截 → 会把「目录写中文、实际是日文歌」这种标签错误也拦掉
  - ✅ 正确：**只在「外文曲目 + 歌词是中文」时拦截**（这才是「匹配到中文翻唱版」的强信号），其余按歌词实际语言决定要不要翻译
- 可疑项**不自动写入**，进「待人工确认」队列

## 六、乱码：来源与识别

库里 178 个外挂歌词文件中，有一批内容本身就是坏的——典型是**占位文本被错误转码**：

```
原文：此歌曲为没有填词的纯音乐，请您欣赏
乱码：森貉Ж峈羶衄沓棵腔曾秞氈ㄛワ蠟釔奼
```

**识别手段**（`fnlrc/library.py::looks_broken()`）：

1. 出现替换字符 `U+FFFD` → 已损坏
2. 把文本按 latin-1 编码再按 GBK/Big5/Shift-JIS 解码，出现占位文本关键词 → 判为 `mojibake:<编码>`
3. 文件为空或只有空白 → 需要重做
4. 注意区分**「合法占位文本」**（正常写着的"此歌曲为纯音乐…"）与**「乱码」**：前者不是损坏，但也不算有歌词，应当尝试重新获取

**处理策略**：坏文件 → 重新抓取 → 抓不到就保留原文件不动（绝不写入"半个文件"）。

## 七、工程坑（每一条都真实踩过）

### 7.1 瞬时失败必须重试，但重试要有上限

批量跑 520 首，网络抖动/限流是常态。没有重试 → 随机丢歌；重试无上限 → 一首慢歌拖垮整轮。**正确姿势**：指数退避 + 全局节流 + 单曲总时限。

### 7.2 全局节流比并发更重要

对 LRCLIB 这类小站，**≥1.2s/次**的全局最小间隔能显著降低 429；网易云 ≥0.35s。宁可慢一点，不要被限流。

### 7.3 Windows 写 SMB 共享目录

- bash 重定向写 UNC 路径（`//192.168.0.2/音乐/x.txt`）**会失败**（`No such file or directory`）
- **Python 原生路径 `\\192.168.0.2\音乐\...` 可正常创建/删除** ✅
- 结论：文件读写一律走 Python 的 `os`/`open`，不要依赖 shell 重定向

### 7.4 文件名会污染搜索关键词

库里存在 `Ayasa绚沙 - 告白の夜 (告白之夜)_hires.flac`、`22.みちしるべ (Short Size).wav` 这类命名。搜索前应清洗：剥掉 `_hires`、`_H`、`(Short Size)`、`【192kHz 24bit】` 等后缀，把 `_` 还原成空格。这能把相当一部分 `no_lyrics` 救回来（**待实现：第二轮补跑**）。
