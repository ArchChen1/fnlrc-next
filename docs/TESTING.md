# 测试策略

> 这个项目的正确性分两层：**文本层的规则正确**（决定飞牛会不会双行）和**系统层的健壮**（500 首批量跑不崩、不写坏文件）。
> 第一层必须用单元测试钉死；第二层用真样本 + 假数据做回归。

---

## 一、测试分层

| 层 | 对象 | 方式 | 是否联网 |
|---|---|---|---|
| 单元 | `lrc.py`：解析 / 双行合成 / **规则校验** | 纯字符串进出，用例即「飞牛边界用例表」 | ❌ |
| 单元 | `library.py`：编码嗅探 / 乱码识别 / 语言预期推断 | 构造字节流与假标签 | ❌ |
| 集成 | `pipeline.process_song` | **stub 掉 providers**（返回固定歌词），验证状态机与写入行为 | ❌ |
| 契约 | providers 的解析逻辑 | 用**真实响应样本**（存为 JSON fixture）验证字段解析与打分 | ❌ |
| 端到端 | 全链路 | 在**临时目录**放 3–5 首真歌（含日语/英语/中文/纯音乐各一）跑一遍 | ✅（可选，标记 `@pytest.mark.network`） |
| 集成 | `fnos.py` 探测 / 计划 / 回填 | 用**合成库**（自己建 `music.db` + 分片，形状照真机）验证两处布局、列猜测、回读校验 | ❌ |
| 手工 | 飞牛实际显示效果 | 写进真库 → 飞牛里看是否双行 | — |

`tests/test_fnos.py` 的合成库**照真机结构指纹造**（`docs/TECH-NOTES.md` 2.5）：

- 主库有 `lyric` 表，但它**只是索引**（`id, guid, track_id, source, stored_guid, …`），**没有正文列**
- 正文在分片的 **`lyric_content`** 表（`guid PK, content BLOB, created_at`）
- 夹具**刻意不含 `isLRC` 列** —— 真机全库没有这个列。谁要是在写入 SQL 里加它，
  这里会直接以 `OperationalError` 暴露，而不是悄悄把虚构的列写进真机

早先这个文件的夹具用的是一张**真机上根本不存在的表结构**（正文放主库、还带 `isLRC`），
于是测试全绿而脚本在真机上必然报「结构与预期不符」。**夹具必须照真机造，
否则测试给的是一份虚假的安全感。**

"只挂一处要报得清"、"关联自检会把命中率打出来"、"权限不足时给可读提示而不是崩溃"、
"给没有歌词的歌建行 / 已有歌词的歌永不新建" 都有专门用例。

**纪律**：CI 里不跑联网测试（默认 `-m "not network"`），避免第三方抖动导致红色。

## 二、必须钉死的用例：飞牛双行规则

`tests/test_lrc_rules.py` —— 用例直接来自实测（见 `TECH-NOTES.md` 1.3）：

```python
CASES = [
    # (名称, LRC 文本, 期望 ok, 期望并行组)
    ("交错成对 4 组",           interleaved(4),                      True,  4),
    ("分段：原文在前译文在后",   grouped(4),                          True,  4),
    ("5 行前奏单语 + 成对",      leading_mono(5, pairs=5),            True,  5),
    ("20 对 + 尾部 3 行单语",    tail_mono(pairs=20, tail=3),         True, 20),
    ("前 10 对 + 后 20 行单语",  tail_mono(pairs=10, tail=20),        False, 10),
    ("只有 3 对",                interleaved(3),                      False, 3),
    ("逐字卡拉OK标签",           karaoke(),                           False, 0),
    ("无时间戳",                 "just text",                         False, 0),
    ("全角括号时间戳",           fullwidth_brackets(5),               True,  5),
    ("[mm:ss] 无小数",           minute_only(5),                      True,  5),

```

测试点还包括：
- **制作名单剔除**：`[00:00.00] 作词 : 某人` 必须不被算作歌词行（否则成对比例被拉低）
- **空行/纯空格行**剔除
- **同一时间戳去重**（同 ms 同文本只留一条）
- **时间戳偏差不应配对**：译文与原文差 10ms 时必须**不**认定为同组（双行靠严格同 ms）

## 三、语言判定用例（历史 bug 防回归）

`tests/test_lang.py` —— 这是**真实踩过的坑**，必须有回归：

```python
def test_japanese_not_chinese():
    # 大量汉字的日文歌词，曾经被误判为中文 → 日语歌只写了单语
    line = "残酷な天使のように 少年よ 神話になれ 蒼い風がいま"
    assert detect_lang(line) == "ja"          # 关键：假名优先

def test_chinese_ok():
    assert detect_lang("我在抽屉里找到你的信") == "zh"

def test_korean():
    assert detect_lang("사랑해요 그대") == "ko"

def test_russian():
    assert detect_lang("Умри если меня не любишь") == "ru"

def test_latin():
    assert detect_lang("I found your letter in the drawer") == "latin"
```

另需覆盖**交叉校验**逻辑：
- 外文曲目（expected=`ru`）+ 歌词 `zh` → `lang_mismatch`，**不写**
- 外文曲目（expected=`latin`，但标签写错）+ 歌词 `ja` → **正常翻译写入**（不能因为标签错误就拦）
- 中文曲目 + 歌词 `zh` → 单语写入

## 四、编码与乱码用例

`tests/test_encoding.py`：

| 输入 | 期望 |
|---|---|
| UTF-8 文件 | 正常解码 |
| UTF-8 BOM | 正常解码（去 BOM） |
| GBK 中文歌词 | 正常解码 |
| UTF-16 | 正常解码 |
| 含 `U+FFFD` 的文本 | `looks_broken() == "replacement_char"` |
| 占位文本被 latin-1 误读的乱码 | `looks_broken()` 命中 `mojibake:*` |
| **GBK 被按 Big5 解码**后存成 UTF-8 | `looks_broken() == "mojibake:gbk-as-big5"`（夹具 `lrc_broken_gbk_as_big5.lrc`） |
| **正常的**中文 / 日文 / 英文歌词 | 不算乱码（反推检测不能误伤） |
| **正常的**「此歌曲为没有填词的纯音乐，请您欣赏」 | 不算乱码（但视为"没有歌词"） |
| 空文件 / 只有空白 | 需要重做 |

> 「GBK 被按 Big5 解码」那一行是**真机实测到的形态**，也是这个检测器存在的理由：
> 它是**合法 UTF-8**、没有替换字符、也不是单字节那类乱码 ——
> 只做 `latin-1 → 其他编码` 这一个方向的反推完全抓不到。
> 所以检测要成对地试「原编码 → 被当成什么解」（`library.MISDECODE_PAIRS`）。
>
> 反面同样重要：错误转码检测很容易**误伤正常歌词**（正常中文当然能"还原"出别的东西），
> 所以判据是"还原后能命中占位文本"，而不是"能还原"。三条不误伤的用例钉住这一点。

## 五、集成测试：状态机

`tests/test_pipeline.py` —— **stub providers**，断言每个分支产出正确的 `status` 与副作用：

| 场景（stub 返回值） | 期望 status | 期望副作用 |
|---|---|---|
| 网易云返回原词+译词 | `written` | 写入双语，并行组 > 0 |
| 网易云只有原词 + 翻译后端可用 | `written` | 翻译被调用一次 |
| 只有原词 + 翻译后端不可用（`translate=none`） | `written_mono` | 写单语，note 说明 |
| 两个源都空 | `no_lyrics` | 不写文件 |
| 两个源都超时（超过 deadline） | `timeout` | 不写文件，可重跑 |
| 源返回中文歌词 + expected=ru | `lang_mismatch` | **不写文件** |
| 已有合规双语文件 | `skipped_existing` | **不覆盖** |
| `--force` + 已有合规双语 | 重做 | 旧文件先备份 `.bak` |
| 目标目录不可写 | `write_failed` | note 含错误原因 |
| 纯音乐（`zxx`） | `skip_instrumental` | 一次网络都不发（用计数器断言） |
| **外文单语 `.lrc` + 源站有译文**（`keep_local` 开） | `written_keep_local` | 输出用的是**本地**时间戳，译文插在同一毫秒 |
| 外文单语 `.lrc` + 源站**没有**译文 | `written_mono` | note 里保留"本地时间轴"的放弃原因 |
| 外文单语 `.lrc` + `keep_local=False` | `written` / `dumped` | 用**源站**时间轴 |
| 本地已是双行 + `--force` | 重做 | 不拿双行文件当基底（`旧译文` 不残留） |
| 本地中文单语 | 不做保留 | 中文歌无需双语 |
| 本地行数 < 4 | 不做保留 | 成对规则本来就过不了 |

### 五之二、译文对齐（`providers.align_translation`）

保留本地时间轴的核心是这一步，所以单独钉：

| 场景 | 期望 |
|---|---|
| 时间戳相差在 ±900ms 内 | 按时间戳配，译文挂到**本地**毫秒上 |
| 同一时刻同时有原文行和罗马音行 | **优先挑带译文的那个候选**（罗马音行没有译文） |
| 时间戳完全对不上、原文文本一致 | 按文本相似度兜底配上 |
| 时间戳远、文本也不像 | 全部留 `None`，`hits == 0` —— **不乱配** |
| 本地两行对应同一个源站行 | 只有先到的那行拿到译文（不重复消费） |

**反向验证是必须的**：把 `Config.keep_local` 的默认值改成 `False` 之后，
`test_pipeline.py` 里应有 4 条断言立刻失败。若没有失败，说明那几条测试是空跑的。

> 「**不写文件**」这类断言比「写了什么」更重要——它是这个项目的安全底线。

## 六之二、人工翻译（M3）

`tests/test_manual.py` 与 `tests/test_server.py` 的人工翻译段。**验收标准直接变成断言**，
其中「导出编码」「填一半」「改原文被拦」「时间轴不动」四条是硬要求（`plan/03` §八）：

| 场景 | 期望 |
|---|---|
| 导出 CSV | 首三字节是 `EF BB BF`（`utf-8-sig`），Excel 才认中文 |
| 导出列 | 含 `file/index/time/original/translation`，`translation` 留空 |
| 填一半行导回 | 填过的行有译文，未填的行**保持原文单语** |
| 导出后改一行 `original` | 导回**被拦下**，`problems` 非空，**不写文件** |
| 导回后半 | 原文行的时间戳与导出前**逐一相等**（不漂移） |
| `index` 不连续 / 重复 | 拦下 |
| 一行都没填 | 拒（写它等于把单语原样覆盖一遍） |
| 副歌同文本重复行 | 按**行的先后**各占一条，不堆到第一条 |
| 中文歌 / 无 `.lrc` / 已是双语 | 不进待译清单（`collect` 直接跳过） |
| 单语里混入罗马音 | 罗马音行被摘掉，不算待译 |
| 记忆库 | 默认**不写**；只记「非中文 → 中文」；原文是中文 / 译文非中文都不记 |
| `/api/manual/lines` | **无需令牌**（返回的是用户自己的歌词文本） |
| `/api/manual/save` | **需令牌**；成功写回并备份 `.bak`；`backup=False` 时不备份 |
| 保存被校验拒绝 | 原文件字节不变（`一个字节都不写`） |

> 与 `test_pipeline.py` 同一条原则：**「不写文件」比「写了什么」更重要**。
> 校验不过时改到半个文件，是最难查的一类事故。

## 六之三、界面语言（M4）

`tests/test_i18n.py`（后端）与 `tests/test_web_i18n.py`（前端）。

i18n 的 bug 有两种形态，**都不会在正常点界面时暴露**：
① 某语言漏了一条 → 界面上冒出一个 `some.missing.key`；
② 占位符写错（`{n}` vs `{num}`）→ 要么抛异常，要么显示成字面量。
所以这两类用**静态断言**钉死，不靠人点。

| 场景 | 期望 |
|---|---|
| 各语言键集合 vs 英文（FALLBACK） | **完全一致**，多一个/少一个都失败 |
| `missing_keys()` | 空 |
| 文案值为空串 / 全空白 | 不存在 |
| 占位符两边一致 | `{n}` 这类在 zh / en 里**逐条相同** |
| 缺 key | 回退英文；英文也没有 → 显示 key 本身（**不空白、不抛**） |
| 传参对不上（少给 `{n}`） | 原样显示，**不抛异常**（不能把 CLI 打断） |
| `normalize` | `zh-CN`/`zh_Hans_CN`→`zh`；`en-US`/`EN`→`en`；`ja`/`""`/`None`→`""` |
| 设了不支持的语言 | **保持当前语言**，不静默变成英文 |
| 优先级 | `FNLRC_LANG` > config 的 `lang` > `zh`（默认仍是中文，老用户升级不变脸） |
| 新增语言 | 往 `_CATALOGS` 登记一行即可用（用假的 `xx` 验证） |
| **前端** zh.js / en.js 键一致、无重复键 | 是 |
| **前端** 占位符两边一致 | 是 |
| **前端** `index.html` 的 `data-i18n*` 键都存在 | 是（漏一个就是界面上冒出键名） |
| **前端** JS 里 `t("...")` 用到的键都存在 | 是 |
| **前端** 动态拼的键（`backend.<x>.hint` 等）都存在 | 是 |
| 前后端同名键（`status.written` 等）中文值 | **完全相等**（防两份词表各写各的） |
| 前端 `LANGS` vs 后端 `available()` | 一致 |

> **数据不翻译**这一点也有测试覆盖：报告里的 `status` 永远是英文枚举，
> 只有展示层映射。所以切语言不会让导出的 CSV 变形。

## 七、性能与批量健壮性

- **单曲时限**：stub 一个「永远慢」的源，断言超时后 song 状态为 `timeout` 且总耗时 < `deadline_s + 3s`
- **不卡死**：构造 50 首「两个源都查不到」的歌，断言整轮能在合理时间内跑完（回归那个「单曲 89.9s → 5.1s」的修复）
- **可中断**：`should_stop()` 返回 True 后，最多再处理完当前一首即停止，已写的文件保留

## 八、端到端

`tests/test_e2e_network.py`（标记 `@network`，默认不跑）。真抓、真合成、真校验、真落盘。

**音频是 0 字节的 `.flac`**，文件名写成「艺人 - 标题」的真实曲目 ——
`read_tags` 打不开就回退到文件名解析（这条兜底路径本身也是被测对象），
所以标题/艺人/目录推断的语言都是真的，能命中真实数据源。代价是拿不到时长，
"时长差 >10s 淘汰"那条由 `test_matching.py` 的离线用例负责。

覆盖：数据源契约（时间戳单调、语言判定、译词有无）、预览全链路**不碰音乐库**、
至少一首外文歌产出合规双语、中文歌不被塞进译文、**纯音乐一次网络都不发**（计数器断言）、
保留本地时间轴、写入模式的 `.bak` 与音频不被改动。

断言的是**行为**不是文本 —— 第三方内容会变，绝不写「歌词等于某段固定文字」。

还想要一条**纯手工**的验收（飞牛里真的显示双行）时，按这套走：

```
e2e_library/
├── 中文/中文歌.flac          （期望：单语）
├── 日语/日文歌.flac          （期望：双语，网易云译词）
├── 英语/英文歌.flac          （期望：双语）
├── 纯音乐/钢琴曲.flac        （期望：跳过）
└── 破损/乱码.lrc + 对应音频   （期望：重建）
```

`python -m fnlrc run --root <该库> --write`，然后确认：状态分布正确、
生成的 `.lrc` 全部 `validate().ok`、旧文件都有 `.bak`、回滚后与原始一致。

## 九、运行方式

先装开发依赖（普通使用不需要）：

```bash
pip install -r requirements-dev.txt
```

```bash
pytest -q                          # 只跑离线用例（默认，pyproject 里 addopts 已排除 network）
pytest -q -m network               # 含联网端到端（手动跑，约 40 秒）
pytest -q --cov=fnlrc              # 覆盖率
```

> **别用仓库里可能残留的 `.venv`** —— 虚拟环境不可移植：开发机上（Windows）建的
> `.venv` 里是 `Lib/` + `Scripts/`，拿到 Linux/NAS 上直接不可用。换机器请重新建。
>
> `requirements-dev.txt` 里除了 `pytest` 还有 **`httpx2`**：新版 starlette 的
> `TestClient` 依赖它，缺了会让 `pytest` **在导入阶段**就失败。本地旧版 starlette
> 只会打一条 deprecation 警告，所以很容易漏 —— 在 NAS 上验证时真踩到过。

覆盖率目标：`lrc.py` 与 `library.py` **≥ 90%**（这两个是正确性地基）；`pipeline.py` **≥ 80%**（状态机分支全覆盖）。

## 十、什么不测

- 不写「快照测试」锁死具体歌词文本（第三方内容会变）
- 不写「断言模型目录里有某个模型」这类变更检测器
- 不测第三方服务本身的可用性（那是运维问题，不是代码问题）
