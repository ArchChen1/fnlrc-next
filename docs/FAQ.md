# 常见问题（FAQ）

## 安全性

**Q：会不会改坏我的音乐文件？**
不会。本工具**只读音频、只写 `.lrc` 文本文件**，不碰音频本体。替换已有 `.lrc` 前会先备份成 `.lrc.bak`，报告页提供一键回滚。

**Q：会不会把我的库搞得一团糟？**
默认开启**预览模式**：先只生成到 `fnlrc_out/` 目录给你看，确认没问题再执行写入。另外「可能匹配错」的歌会被单独拦到「待人工确认」，不会自动写。

**Q：会上传我的音乐或隐私吗？**
不会上传音频。默认模式下只发送**歌名、艺人、专辑、时长**这类元数据用于匹配歌词 ——
这是默认路径唯一的出网流量，而且不包含歌词内容。

只有你显式选了「AI 翻译」并配了 key，才会把**歌词文本**发给所配置的端点。
默认的「源站译词」模式完全不发歌词。

**Q：网页版部署时，AI 翻译的 key 会泄露吗？**
不会。Key **只存在服务端**（环境变量优先，否则 `config.json`），浏览器永远拿不到回显 ——
页面上只能看到"已配置"和一个掩码（如 `sk-123***cdef`）。前端代码里也没有任何地方能碰到它。

两点要注意：

1. **网页版必须靠访问令牌保护**。任何人只要能访问那个端口，就能触发扫描和**写入**你的音乐库。
   令牌在启动日志里（`docker logs fnlrc | grep -i token`），怀疑泄露可以重置。
2. 如果 API key 是通过环境变量 `FNLRC_REMOTE_API_KEY` 提供的，设置页里的 key 输入框会变成只读 ——
   避免"一份 key 两个真相"。

**Q：为什么绑在 127.0.0.1 还要令牌？**
因为**绑回环不是授权边界**：你机器上任何进程、以及任何能触达 `http://127.0.0.1:<端口>` 的网页
（DNS rebinding / localhost CSRF），都能对这个服务发请求。所以写操作一律要令牌 + 同源校验。

## 使用门槛

**Q：需要显卡吗？**
不需要。整个工具是纯 CPU 的：抓歌词、修乱码、合成双语都不涉及推理。
（早期版本有个可选的本地模型翻译后端要显卡，已经下线了。）

**Q：需要花钱吗？需要 API key 吗？**
都不需要。默认走**源站自带的中文译词**（网易云），零成本、零配置、也不出网。
只有源站没给译词、你又想要译文时，才需要配一个自己的 key（DeepSeek 或任意 OpenAI 兼容端点，折合几分钱一千首）。

**Q：会不会偷偷联网？我只想用源站译词。**
不会。默认后端 `source` **一次后端请求都不发** —— 源站没给译词就写单语。
只有显式选「AI 翻译」时才会调用你所配置的端点。

**Q：为什么不支持本地模型（Ollama）了？**
它对默认体验没有贡献：要你先装模型、占显存，而它的收益只是"省一点 API 费用"——
可默认路径本来就不花钱。而维护成本全在边界上（模型缺失、冷启动、显存、容器网络、思考模式吃光输出预算）。
想完全不联网，用默认的「源站译词」就够了。
如果你有自建的大模型服务（vLLM / one-api 之类），把它填进「AI 翻译」即可，它是 OpenAI 兼容协议。

**Q：需要懂命令行吗？**
不需要。桌面版双击即用；网页版一条 docker 命令。

详细的界面walkthrough见 [GUIDE.md](GUIDE.md)；两种形态各自的安装部署见
[GUIDE-DESKTOP.md](GUIDE-DESKTOP.md) 和 [GUIDE-WEB.md](GUIDE-WEB.md)。

**Q：支持 macOS / Linux 吗？**
核心代码跨平台。Docker 版在 Linux/macOS 都能跑；桌面版目前优先 Windows，Linux/macOS 需要系统 WebView 组件（打包在工作计划中）。

## 效果相关

**Q：为什么很多歌查不到歌词？**
三类原因：① 确实冷门，两个源都没有；② **文件名太脏**（`_hires`、`(Short Size)`、`【192kHz 24bit】` 这类后缀污染了搜索词）；③ 外网不通（LRCLIB 在墙外）。

② 现在已经缓解：程序会剥掉已知的噪声后缀再搜一次（只剥清单里的，`Bella ciao (啊朋友再见)` 这类合法标题不会被误伤）。剩下查不到的，会在报告里归到「无歌词」，可以换后端补翻或过一阵重跑。

**Q：为什么有的歌显示「待人工确认」？**
因为出现了**外文歌匹配到中文翻唱版**的情况（标题、时长都对得上，但歌词是中文的，比如俄语歌匹配到中文演唱版的词）。这种情况下时间轴可能对不上，所以程序**故意不自动写**，让你决定。

**Q：翻译质量不满意怎么办？**
按优先级试：① 大多数歌其实用的是源站**人工/字幕组译词**，质量已经不错；② 填自己的 API key 用大模型补翻源站漏掉的行；③ 自己译好再手动替换那个 `.lrc`。

注意机器翻译**只会用在源站没给译文的那几行上** —— 已经有人工译词的地方不会被机器覆盖。

**Q：机器翻译的歌词准吗？**
日常歌词够用，但有明确短板：**句式绕、含双关或典故的句子容易翻反**。
源站译词是人工/字幕组做的，质量更好 —— 所以程序优先用源站译词，机器只补它漏掉的行。官方/正式场合建议人工过一遍。

**Q：写完歌词，飞牛里为什么没变化？**

**这是预期行为，不是 bug。** 飞牛只在**歌曲首次被解析（入库）时**读一次同目录的 `.lrc`。
路径一旦入库，之后就**永远不再重新解析** —— 扫描、改 mtime、重写文件、甚至把文件移出再移回，
全部无效（实测 6 种方式）。它把旁挂歌词当成"一次性输入"，而不是可变更的资产。

（另一个独立原因是**音频里内嵌了歌词**：飞牛的优先级是「内嵌 > 外挂」，外挂文件永远盖不住它。）

**所以正确的工作流是反过来：新歌先补完，再入库。**

```
新歌 → 放到暂存目录（不在飞牛音乐库里）→ fnlrc 补完 → 整首移进音乐库
```

对**已经入库**的歌，没有零成本的办法，只有三条路：

| 出路 | 歌单/收藏/历史 | 代价 |
|---|---|---|
| **用它自己的歌词功能**（手动关联 / 本地歌词） | ✅ **不受影响** | 纯界面操作、零风险。**但它得支持读本地文件**，否则会把你的译文覆盖成它的在线单语版 |
| **改它的歌词库**（原地写歌词正文，保留原 `lyric_id`） | ✅ 全部保留 | 要访问 NAS 上的**两处**应用数据目录（主库在系统盘 `@appdata`、歌词正文在存储池 `@appmeta`，通常要提权），属于改别的应用的数据库，飞牛改表结构就会失效 |
| **删库重扫**（把音乐库移除再重新添加） | ❌ **全丢**（所有 `track.guid` 会变） | 界面就能做、必然有效；但歌单/收藏/播放历史/歌词偏好全部失效，全库重扫，云端元数据偏好还会重新刮削 |

**怎么选、每条的详细做法与验证步骤，见专文 [docs/FNOS-SIDECAR.md](FNOS-SIDECAR.md)** ——
里面有决定树、操作清单、以及「删库重扫」动手前该算清楚的账。

动手改数据库前**务必备份** `music.db` 和整个 `lyric-sqlite/` 目录。

**Q：歌词显示成一行一行的原文和译文，不是并排的两行？**
飞牛的双行显示是「同一时间戳两行 → 归为一组，一起高亮滚动」。本项目就是按这个规则生成的，并在写入前用它的规则做过校验（≥4 组成对、成对比例 ≥80%、前奏单语 ≤8 行、不与逐字卡拉OK混用）。如果某首没双行，报告里会明确标出原因。

**Q：为什么只有原文和译文，罗马音去哪了？**
罗马音被**刻意排除在文件之外**。网易云会同时给出原词、中文译词和罗马音，但把三行写进同一个时间戳，
飞牛会把它们当成一组三行一起滚动 —— 那不是想要的效果。所以本项目只输出「原文 + 译文」两行，
罗马音会被单独识别出来保留（报告里能看到），需要时可以在输出策略里打开。

顺带一提：有些上传会把罗马音直接混在 `lrc` 字段里（一行原文一行罗马音），
这类会被自动识别并剥掉，不会混进原文。

**Q：为什么这首歌写成了单语？**
两种原因：① 源站没有译词，而你选的后端（默认是「源站译词」）也不会去翻；
② 源站译词只覆盖了一部分行，双语文件的成对比例达不到 80%，过不了飞牛的规则 ——
这时候会**退回写单语**，而不是什么都不写。

想提高覆盖率就把后端换成「AI 翻译」再重跑一次；已经写好的文件会自动跳过，不会重复劳动。

**Q：我已经有一份外文单语歌词，而且时间轴是自己一句一句对过的，会被换掉吗？**

**默认不会被换掉。** 这是「保留本地时间轴」模式，默认开着。

程序会解析你那份 `.lrc`，**沿用它的时间轴和断句**，只把网上找到的译文按**相同的时间戳**插进去 —— 原文行一个字不动，时间戳一个也不改。配对顺序是：时间戳就近（±0.9 秒）→ 原文文本相似度兜底 → 配不上就留空（宁可不补，不乱配）。

如果这样拼出来过不了飞牛的双行规则（网上给的译文覆盖太少），会**自动退回重抓**，并在报告里写明原因。

**不想要这个行为**：网页版「设置 ⚙」→「其它」取消勾选「外文单语歌词：保留本地时间轴，只把译文插进去」；命令行加 `--rebuild-local`。关掉之后就一律按源站整份重写。

两个例外：本地文件**已经是双行**时不走这条路（那属于"已是合规双语"，该跳过就跳过）；`--force` 强制重做时也不走（强制重做 = 从源站整份重来）。

**Q：有些歌词文件打开就是乱码，重刮能救回来吗？**

**多半救不回来，而且程序会告诉你原因。**

乱码往往不是这一份文件的问题，是**源头就坏了**。真实见到过的一种：GBK 编码的中文被按 Big5 解码，再存成 UTF-8 —— 这种文件表面上是合法 UTF-8、能正常打开，只是里面的字全是错的（"看着像中文，其实是别的字"）。重刮回来的还是同一个坏源头。

所以程序会把乱码的**形态**写进报告（例如 `mojibake:gbk-as-big5`），而不是笼统说一句"重来过"。看到这种提示，正确的做法是找到这首歌的正确原文、手工放一份 `.lrc` 进去，或者干脆让它保持单语 —— 都比挂一份乱码强。

## 兼容与限制

**Q：支持哪些音频格式？**
mp3 / flac / m4a / wav / ogg / ape / wma / dsf / aac / opus。歌词文件始终是标准的 `.lrc`（UTF-8）。

**Q：支持哪些语言？**
中文、日语、英语、韩语、俄语、法语、德语、西班牙语等——取决于源站覆盖。任何「非中文」的歌词都会被翻译成中文形成双语；中文歌保持单语（不需要译文）。

**Q：纯音乐会被塞歌词吗？**
不会。通过 `language=zxx` 标签（无语言内容）+ 源站 `instrumental` 标记 + 文件名关键词三重判断，纯音乐直接跳过。

**Q：能把歌词写回音频文件（内嵌）吗？**
当前版本只写外挂 `.lrc`。内嵌写入/清理在路线图里（因为涉及改写音频文件，风险更高，需要单独设计 + 二次确认）。

**Q：能只处理某个目录或几首歌吗？**
可以。命令行的 `--only <关键词>` / `--limit N`，以及 UI 里的目录筛选都支持。

**Q：能定时跑吗？**
可以，用 CLI + cron（见 `docs/DEPLOY.md`）。已有的合规双语文件会自动跳过，所以每天跑一次只处理新歌，通常几十秒。

## 合规

**Q：会不会有版权问题？**
本项目只做「抓取公开歌词 + 合成 + 写入你自己的音乐库」，**不内嵌、不托管、不分发任何歌词数据**，也不会把歌词上传到任何地方。歌词版权归原作者与版权方所有，请仅用于**个人音乐库整理**。

**Q：会把我封 IP / 封号吗？**
内置了全局节流（网易云 ≥0.35s/次、LRCLIB ≥1.2s/次）+ 指数退避，单曲处理在 10 秒量级。正常使用不会触发风控；不建议把并发调得很高。

**Q：第三方接口哪天挂了怎么办？**
数据源做了多源降级（网易云 → LRCLIB → 你配的翻译后端）。某一个源失效时程序自动降级而不是整体失败。
歌词源已插件化：加一个源只需在 `$FNLRC_DATA/plugins/` 放一个新文件（实现 `available()` + `fetch()`），**不改核心**；模板见 `docs/provider-template.py`，`fnlrc provider list` 能看每个源的可用性。

真实案例：2026-09 网易云把搜索路由 `/api/search/get/web` 停用了（恒返回 `code:405`，
HTTP 还是 200），主源等于全废。代码现在按顺序试两条路由 —— 单个源失效不会让整个工具失效。
