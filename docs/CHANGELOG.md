### 新增
- **歌词源插件化（M2）**：把「数据源」抽象成统一协议，内置的网易云 / LRCLIB 也变成插件；
  社区想加 QQ 音乐 / 酷狗 / Musixmatch，只需新建一个文件，**不改核心**。
  - **新增一个源 = 新增一个文件**：把 `xxx.py` 丢进 `$FNLRC_DATA/plugins/`，实现
    `available()` 与 `fetch()` 即可，`pipeline.py` 一行不用动。
  - **官方也是插件**：内置源（`fnlrc/providers/builtin/`）用同一套协议注册，
    做到「官方 = 插件」的一致性。
  - **一个坏插件不影响别人**：语法错 / import 崩 / `register()` 抛异常，只记日志、
    继续加载下一个，绝不拖垮整体运行。
  - **编排统一降级链**：`fetch_lyrics()` 按 priority（网易云=10 → LRCLIB=20）依次问每个
    可用源，第一个给出可用结果的即采用；单个源取词抛异常会被隔离（但若**所有源都炸**，
    会如实报成 `error` 而不是误报「没有歌词」）。
  - **可筛源**：配置 `providers_enabled`（白名单）/ `providers_disabled`（黑名单，
    优先级更高）。各插件的自有凭据存 `provider_keys`，与 `remote_api_key` 同等敏感，
    只存服务端、不进日志/报告。
  - 命令：`fnlrc provider list`（列出所有源与可用性原因）、
    `fnlrc provider test <源> --file <歌>`（对单个源跑一次契约自检）。
  - 插件模板见 `docs/provider-template.py`（复制即用）。

- **监听文件夹（M1）**：盯着一个目录，新歌下进来就自动补完，不用每次手动点。
  适合配合下载器 —— 下到「待整理」文件夹，这边补完歌词并（可选）搬到音乐库。
  - **纯轮询**（不依赖文件系统事件），所以 SMB / 容器挂载上也能用，且不给项目增依赖。
  - **只碰"看起来下完了"的文件**：连续两轮大小+mtime 不变才算稳定（静默期，默认 8s）；
    `.part/.tmp/.crdownload/.!ut/.aria2` 等临时文件直接忽略。
  - **查到歌词之前不动你的文件**：缺词的歌原地重试（退避 60s/300s/1800s，最多 3 次），
    不会因为"这次没查到"就被搬走。
  - **搬运先复制、成功再删源**：跨盘失败会留下源文件，不会"删了源、目标没写成"。
  - **撞名时新的上位、旧的退 `.bak`**，已有备份绝不覆盖（退成 `(1).ext.bak`）。
  - **状态落盘**（`watch-state.json`）→ 重启不重跑未变化的文件；文件变了才重跑。
  - 危险操作默认关：面板上默认**只预览不写**；`--dry-run` 连 state 都不落盘。
  - 网页版「设置 → 监听文件夹」可配：监听目录、补完后（留原地/复制/移动）、
    音乐库目录、是否直写 `.lrc`、静默秒数、轮询间隔、是否随服务自动启动。
    新增「开始/停止监听」按钮与实时事件日志（SSE）。
  - 命令行：`fnlrc watch --root <目录> [--no-write|--dump] [--after keep|copy|move] [--move-to …]`
  - 服务端启动钩子：配置里开了 `watch_autostart` 就会在进程起来时自动开始监听
    —— 容器重启后监听不中断。

- **首次使用引导**（欢迎 → 填访问令牌 → 选音乐库）。全新环境第一次打开网页时，
  不再是裸弹一个令牌框，而是有三步带你走完的引导。
  - **何时出现**：首次登录 / 没有 `config.json` / **`config.json` 损坏**（这时走完引导会顺手修好）。
    已有配置（`last_root`）直接进主界面；点过「完成」或「跳过」后也不再弹（`setup_done`）。
  - **本机访问会自动跳过「令牌」一步**（服务端已把令牌注进页面），只留「欢迎 → 选库」两步；
    局域网 / 容器打开才要手填。
  - 新增**只读**的令牌校验接口 `GET /api/auth`（令牌 + 同源校验，与写操作同一套守护），
    引导用它确认令牌对不对 —— 不拿写接口去试错。
  - 「跳过引导」只是这次不看，下次仍会出现；「完成」才记为不再引导。
  - 不改变现有令牌机制：引导结束后仍回落到原来的令牌闸门。

- **外文单语歌词：保留本地时间轴，只补译文**（默认开）。
  这类歌以前是**联网重抓、整份覆盖** —— 对"时间轴自己一句一句对过"的用户是净损失。
  现在改成：解析已有的 `.lrc`，沿用它的时间轴与断句，把译文按**相同时间戳**插进去，
  原文行与时间戳一个都不改。
  - 配对顺序：时间戳就近（±0.9s，优先挑有译文的候选）→ 原文文本相似度兜底 → 配不上就留空
  - 拼出来过不了飞牛双行规则时**自动退回重抓**，并把原因写进报告的 `note`
    —— "以为保住了时间轴、其实被换掉"是最需要被告知的情况
  - 不适用：本地已是双行文件（那属于"已是合规双语"），以及 `--force`（强制重做 = 整份重来）
  - 关闭方式：网页版「设置 → 其它」取消勾选，或命令行 `--rebuild-local`
  - 报告里是独立状态 `written_keep_local`（「✓ 双语·留本地轴」），与普通 `written` 分开计数
  - 顺带修掉一个死标签：`decide()` 早就把这种情况标成 `bilingualize`（"外文单语歌词 → 补成双语"），
    但 `bilingualize` 全仓库零消费者 —— 界面上的承诺一直没有代码去做

- **给"一行歌词都没有"的歌新建歌词行**（`--allow-insert`，默认关）。
  真机受控实测确认这条路可行 —— 应用立即接受，不用碰偏好表。这解开了真机上 142 首
  （约四分之一，通常正是最想补的）此前**完全填不了**的死结。
  - **已有歌词的歌永远不会被新建**：实测给已有歌词的曲目插第二条，`preferred` 仍停在旧行，
    用户会以为没生效（要同时 upsert 偏好才行）。本工具从根上不碰这个坑，一律原地更新
  - 新建行的 `guid` / `stored_guid` 格式**从真实行里学**（学不出就拒绝新建，宁可不动）
  - `source` 写 **2**（同目录旁挂），不写 3（在线刮削）

### 修复
- **飞牛歌词库的数据模型整体写错了，已按真机结构指纹改正**（2026-09-15）。这是本轮最重的一处：
  上一版把"正文放在主库的 `lyric` 表、还有一个 `isLRC` 列"当成事实，而那个表结构真机上**不存在**。

  | 真机事实 | 上一版的假设 |
  |---|---|
  | 分片里的正文表叫 **`lyric_content`**（`guid PK, content BLOB, created_at`） | 以为叫 `lyric` |
  | 主库的 `lyric` 表是**索引**（`id, guid, track_id, source, stored_guid, …`），**没有正文** | 以为正文在主库 |
  | **全库没有 `isLRC` 列**（搜过所有表） | `SET isLRC = 1` |
  | 关联靠 `lyric.track_id` → `track.id` | 用 `track.guid == stored_guid` 直接相等 |
  | 分片名 `"lyric-%02x.db" % int(stored_guid[0],16)`，**两位零填充** | 无零填充概念 |

  后果不是"少拿点数据"，而是探测**直接判「结构与预期不符」** —— 这就是真机上卡住的那一步，
  即使上一轮修好了路径也仍然会失败。**更糟的是测试夹具是照着同一个不存在的 schema 编的**，
  所以 231 项测试全绿也说明不了任何事。

  - `fnos.py` 的 `discover` / `plan` / `apply_plan` 全部按真机模型重写
  - `tests/test_fnos.py` 的夹具换成**真机 schema**，且**刻意不含 `isLRC`** ——
    将来谁再写 `isLRC` 会立刻报错，而不是悄悄把虚构的列写进真机
  - 探测报告新增**关联自检**：把「用 `stored_guid` 还是 `guid` 去分片查正文」两种假设都测一遍、
    都报命中率（真机 100% vs 0%），而不是我们悄悄猜一个
  - 分片「编号命中」原来拿 guid 去比**零填充后的**分片后缀，真机上会假报 `0/N`；改成比编号
- 修 `fnlrc/cli.py` 两处会让命令**直接崩**的问题：
  - 中文 Windows 控制台是 cp936，输出里的 `✅` / `⚠` 编码不了会抛 `UnicodeEncodeError`
    把命令整个打断。现在统一 `errors="replace"`（`fnos.py` 单独跑时本来就有这层保护，
    走 `python -m fnlrc fnos` 这条路没有）
  - `Path` 没导入 —— 打印失败清单时 `NameError`（只在有失败项时触发，所以一直没暴露）
- `plan()` 返回的是 `Path` 对象，`--json` 那条路会以 `TypeError: not JSON serializable` 崩掉
- `/api/fnos/preview` 的 `samples` 还在取一个已经不存在的 `guid` 键
- **飞牛数据路径模型错了，已在真机上改正**（2026-09-15）。0.0.2 把飞牛的数据当成"一个目录里
  能找到全部"，真机核实后发现是**两块盘上的两处**：
  - 主库 `music.db` 在**系统盘** `/usr/local/apps/@appdata/trim.music/db/music.db`
  - 歌词正文在**存储池** `/vol2/@appmeta/trim.music/lyric-sqlite/lyric-*.db`（16 个分片）
  - `/vol2/@appdata` 里**没有** `trim.music`；歌词正文也**不在** `music.db` 里

  飞牛本身**没有**改表结构（线上表/列与应用自带的 `sqlite.sql`+v2+v3 完全对得上）。
  0.0.2 报的"结构与预期不符"，是探测的路径预期错位造成的误判。
  - `fnlrc/fnos.py` 拆成 `--app-data` / `--appmeta` 两个参数（旧的 `--data-dir` 保留兼容）；
    探测报告改成**两行独立打勾**（主库目录 / 歌词分片目录），只挂一处时一眼能看出来
  - 探测报告新增「真机上的表名列名」原样回显 —— 再报"结构不符"时不必猜，照着那两行定位
  - 分片 guid 列的选取改为**优先匹配 `stored_guid`**：表里若同时有 `guid` 和 `stored_guid`，
    原来的模糊匹配会取到列序靠前的那个，而分片规则用的是 `stored_guid`
  - CLI / 服务端 / 前端设置面板 / 所有文档与示例命令同步改成两处路径
- **乱码检测漏掉了「GBK 被按 Big5 解码」这一形态**。真机实测到的就是这种：
  GBK 的中文被按 Big5 解、再存成 UTF-8 —— 结果是**合法 UTF-8**、没有替换字符、
  也不是单字节那类乱码，只查 `latin-1` 反推完全抓不到。
  `looks_broken()` 现在会成对地试「原编码 → 被当成什么解」（新增 `MISDECODE_PAIRS`），
  返回具体的形态（如 `mojibake:gbk-as-big5`）
- `decide()` 对乱码只说"重新获取"，现在会**说明是哪种乱码**并点明"重刮多半还是同一
  来源，需要你提供正确原文" —— 乱码的根因常在源头，重试是无效动作。
  空文件与乱码的原因不再混成一句
- 文档里 `lyric.source` 的优先级编号写反了（写成 `内嵌(4) > 旁挂(3) > 在线(1)`）；
  实际枚举是 `1`=内嵌、`2`=旁挂、`3`=在线刮削、`4`=手动关联
- **`scripts/probe_write.py` 的写权限探针会在回收站留东西**。探针是「建了再删」，
  而飞牛（以及开了回收站的 SMB 共享）会把删除路由进回收站 —— 每测一个目录就多一条
  `fnlrc_write_test.tmp` 记录。真机上实测到 17 条。现在：默认只抽 8 个子目录
  （`--subdirs N` 可调，`--subdirs 0` 完全不测），并且明确打印说明。库内一直是干净的

### 修复（来自 NAS 真机验证）

- **`--only` 与 `--limit` 一起用是坏的**。`cli.py` 先 `scan(limit=N)` 按遍历顺序截断、
  再拿 `--only` 去过滤 —— `--only 英语 --limit 3` 会**空选**、打印「没有要处理的歌」、
  退出码 1。两者单独用都正常，合起来才坏。
  现在顺序固定为**先筛、再截**，而且只写在 `library.select()` 一处，CLI 与网页版都调它。
  筛选在加载标签之前做（`rel` 只是 `relpath`），所以 `--limit` 依然省时间。
- **网页版的 `only` 是个死参数**：`_config_from()` 收下它、`Config` 存着它，
  但 `pipeline` 从头到尾没有消费者，`/api/preview` 与 `/api/run` 也都不按它过滤 ——
  接口承诺是假的。现在真的过滤，`Config.only` 这个空转字段一并删掉。
- **三条测试在装了飞牛的机器上必红**。它们靠「自动探测找不到飞牛」：
  非 root 跑抛 `PermissionError`，root 跑探测成功而断言要 `not_found`。
  即在它要服务的机器上永远红，CI 绿只是因为 CI 里没有飞牛。
  改成传**显式空目录**（与环境无关），并补了自动探测路径的独立用例。
- **`_music_db()` 撞到不可读目录直接抛 `PermissionError`**，用户看到的是 traceback，
  而不是文档承诺的那句可读提示。根因：`Path.is_file()` **只吞**
  `ENOENT/ENOTDIR/ELOOP`，`EACCES`/`EPERM` 是重新抛出的 —— 而飞牛的
  `@appdata` / `@appmeta` 正是 `770 root:root`。现在统一把"没权限"当成"没找到"。
- **给了路径就以它为准，不再回退自动探测**。用户明确指了一处路径，我们却因为那里
  没有 `music.db` 而改用别处的库去写 —— 比直接说"这里没有 music.db"危险得多。

### 修复（DeepSeek 接口按官方文档校正）

- **base_url 与模型名都写错了**。按 `https://api-docs.deepseek.com/zh-cn/` 校正：
  - base_url 是 `https://api.deepseek.com`，**不带 `/v1`**（带 `/v1` 实测仍能通，但以文档为准）
  - 模型名只有 `deepseek-flash` 与 `deepseek-v4-pro`；我们写的 `deepseek-chat` 已不在文档里
- **思考模式没关掉 —— 这个后果比上面两条严重**。DeepSeek 的 `thinking.type`
  **默认是 `enabled`**、默认强度 `reasoning_effort: high`。翻译这种任务上思考链是纯负担：
  思考 token 照计费、慢，而且会**吃掉 `max_tokens` 的预算** —— 思考占满则正文为空，
  `_parse_numbered` 拿不到译文，90% 门槛不过，**整首降级为单语**。
  官方文档还写明 `temperature` 在思考模式下不生效，所以我们一直发的 `0.1` 也是空设。
  - 现在只在**主机名含 deepseek** 时才发 `thinking: {"type": "disabled"}`；
    万一被 400 拒掉会**去掉它重试一次**（one-api / vLLM / LM Studio 这类严格端点不接受未知字段）
  - 关掉思考后 `temperature: 0.1` 才真的生效
- **「测试连接」的 `max_tokens` 从 64 提到 512**：万一对面关不掉思考模式，
  64 个 token 会被思考链吃光、正文返回空，那会被误报成"连接有问题"。
  空内容时的提示也改成说人话（点明可能是模型名不对或思考链吃光了预算）。

### 计划中
- 二轮补跑器：对 `no_lyrics` / `timeout` 自动重试（换关键词、用专辑名/罗马音）
- provider 插件化（QQ 音乐 / 酷狗 / Musixmatch 可选接入）
- 内嵌歌词的检测增强与「清除内嵌」可选操作
- 人工翻译导入 / 导出
- macOS / Linux 桌面打包
- **多版本共存**：同一首歌保留多个歌词版本，并同步 upsert 偏好表
  （真机实测过做法：只 INSERT 不同步偏好则 `preferred` 停在旧行，用户看不到新版本。
  收益不明确而风险实打实，所以本版只做"原地更新"与"给无歌词的歌建行"两种）

  也不生效"这个平台限制（见 `docs/TECH-NOTES.md` 2.3）：原地更新 `lyric_content` 并
  **保留 `lyric_id`**，所以歌单、收藏、播放历史、歌词偏好全不受影响。

    不需要装 fnlrc、不需要 Docker
  - 探测与差异计划**全程只读**（`mode=ro`，物理上写不进去）；不加 `--apply` 绝不写一个字节

### 修复（会实际影响结果的）
- **启动日志里的令牌变成可 grep 的**：原来打印的是中文提示，而文档让用户跑
  `docker logs fnlrc | grep -i token` —— 中文里没有 "token" 三个字母，那条命令什么都抓不到。
  现在令牌单独打成 `FNLRC_TOKEN=xxx`，照文档做就能拿到
- **打包脚本补上 `pywebview`**：`requirements.txt` 里它是注释掉的（服务器用不到），
  但桌面版少了它，打出来的 exe 不会开原生窗口、只会弹浏览器

- **网易云搜索主路由失效**：`/api/search/get/web` 现恒返回 `code:405 操作频繁`（HTTP 200 但结果为空），
  同一秒内 `/api/search/get` 正常 —— 是路由被停用而不是限流。
  不修的话主源等于全废、全库只剩 LRCLIB 兜底（而它不提供译词）→ 双语功能整体失效。
  现在按顺序试两条路由，第一个有结果的即采用（见 TECH-NOTES 4.1）
- **版本标记降权静默失效**：`version_penalty` 先把标题过了一遍噪声剥离，而版本标记本身就写在
  噪声清单里 —— 先剥再找等于永远找不到。实测导致 `告白の夜 (live version)` 被当成匹配结果
- **MP3 / M4A 的标签从来没被读到过**：mutagen 对不同容器暴露的键完全不同
  （Vorbis → `title`，ID3 → `TIT2`，MP4 → `©nam`），只按友好名查会静默失败、
  一路退到文件名兜底。现在三种容器都做了别名映射
- **部分翻译导致整首降级为单语**：默认后端下只要有一行没有源站译文，整首就退回单语，
  已经拿到的译词全部丢弃。现在两种产物都构造、按飞牛规则择优；
  **单语被显式声明为永远可接受**（`validate()` 对单语恒为 False，让它走校验会导致一个文件都不写）
- **LRCLIB 兜底的歌永远只能写单语**：它的候选所有行都没有译文，默认配置下无从补齐
- **匹配失败被伪装成纯音乐跳过**：「文件名像纯音乐但没匹配上」原本报 `skip_instrumental`，
  进不了任何重试队列 —— 匹配失败就永远查不出来。现在归到可重试的 `no_lyrics`
- **`_ne_lyric` 不收 `deadline`**：单曲时限在取词环节失效

### 重要更正

- **推翻「写完 `.lrc` 点一次扫描就生效」的前提**。实测证明飞牛只在歌曲**首次入库**时读一次旁挂歌词，
  已入库的路径永远不会被重新解析（扫描 / 改 mtime / 重写 / 移出移回，6 种方式全部无效）。
  文档、CLI 输出、UI 提示、报告页文案已全部更正，默认工作流反转为「新歌先补完再入库」。
  存量歌的三条出路与代价见 `docs/FAQ.md`，实测矩阵见 `docs/TECH-NOTES.md` 2.3，决策记录见 ADR-015

### 安全
- API key **只存在服务端**：环境变量优先，否则 `config.json`（0600）。浏览器永远拿不到回显
- 写操作要访问令牌 + 同源校验；**绑回环不算授权边界**（本机任何进程都能发请求）
- `Config.remote_api_key` 加 `field(repr=False)`；新增 `mask_secret()` 统一清洗日志/异常/报告
- `remote_base_url` 落盘前剥掉查询串（挡 `?api_key=` 形态）
- `.gitignore` 补上 `config.json` / `.env` 等凭据文件

### 变更
- 翻译后端语义改为 `source`（默认，不调后端）/ `remote`（自有 API）/ `none`
- 罗马音默认**不写进 `.lrc`**：只输出「原文 + 译文」两行。
  三行挤在同一时间戳会让飞牛把整组当三行滚动
- **移除本地模型（Ollama）后端**。它对默认体验没有贡献（默认路径本来就不花钱），
  维护成本却全在边界上：模型缺失、冷启动、显存、容器网络、思考模式吃光输出预算。
  想完全不联网用默认的「源站译词」；有自建推理服务的可以填进「我的 API」（OpenAI 兼容）。见 ADR-014
- 翻译阶段用独立时限（默认 180s），不与 25s 的抓取时限共用

## [0.0.1] — 2026-09-14 · 脚手架与技术验证

### 新增
- **`fnlrc/lrc.py`** — LRC 解析、规整、双语合成、**飞牛双行规则校验**

  - 乱码识别（替换字符、占位文本被错误转码）

  - 12 种状态的结果模型（`written` / `written_mono` / `no_lyrics` / `timeout` / `lang_mismatch` …）
  - 语言交叉校验：外文曲目抓到中文版歌词 → **拦截不写**
  - 预览模式（写 `fnlrc_out/`）、写入前 `.bak` 备份、已合规文件自动跳过

### 修复（来自真实批量任务）
- 日语歌被判定为中文，导致整库日语歌丢失双语 → 假名优先判定
- 语言校验过严，把「目录名与歌曲实际语言不符」也拦掉 → 改为仅在「外文曲目 + 中文歌词」时拦截
