# 路线图

> **一句话**：给飞牛音乐做一个**傻瓜式歌词补完器**，把「只有原语言单行、经常刮错、乱码、
> 没歌词」变成**原文 + 译文双行**；桌面端双击即用，也能一条命令部署到网页 / NAS；
> **不需要显卡、不需要任何 key，开箱即用**。

已发布的内容见 [CHANGELOG.md](CHANGELOG.md)；技术选型与取舍见 [DECISIONS.md](DECISIONS.md)。

---

## 一、目标与定位

| 问题 | 现状 | 目标 |
|---|---|---|
| 只有原语言 | 日语 / 英语歌看不懂 | 生成飞牛可识别的**双行** LRC |
| 经常刮错 | 匹配到同名曲 / 翻唱版 / 器乐版 | 打分 + **语言交叉校验** + 「可疑项不自动写」 |
| 乱码 / 没歌词 | 占位文本被错误转码、源里查不到 | 编码嗅探 + 乱码识别 + 多源降级 |
| 门槛高 | 会抓歌词的工具要么要命令行，要么要配模型 / Key | 桌面双击可用；零配置默认有译词 |
| **已入库的歌补了没用** | 飞牛只在首次入库时读一次旁挂 `.lrc` | 无法从文件侧解决；改为直接写它的歌词库（保住歌单） |

**非目标**：不做播放器、不做歌词托管 / 分发、不改音频文件本体、不做音乐库管理。

---

## 二、目标用户与场景

| 用户 | 场景 | 关键诉求 |
|---|---|---|
| 普通飞牛用户 | 库里几百首日语 / 英语歌全是单语 | 双击、点两下、完事 |
| 折腾党 | 想把 NAS 上的库一次补齐 | 部署到 NAS，跑一次，可定时 |
| 不想出网的人 | 只想要原文 + 译文的双行，不想把歌词发给第三方 | 默认路径完全不调后端 |
| 脚本党 | 想在 CI / cron 里跑 | CLI + 退出码 + 报告 JSON |

## 三、功能清单

### 已完成

**抓取与合成**
- [x] 库扫描（本地 / SMB / 映射盘）与概览（已有双语 / 单语 / 缺歌词 / 乱码 / 纯音乐）
- [x] 多源抓取：网易云（原词 + 中文译词）→ LRCLIB 兜底
- [x] 匹配打分：标题清洗、版本标记降权、**时长硬淘汰**、语言加权、候选池回显
- [x] **飞牛双行规则校验**（写前预判会不会双行；不通过就退回单语，而不是不写）
- [x] 只输出「原文 + 译文」两行；罗马音识别出来但不落盘
- [x] `.bak` 备份；已合规文件自动跳过
- [x] 纯音乐（`zxx`）零成本跳过、语言不一致拦截、超时可重试

**覆盖率与体验**
- [x] 乱码修复：编码嗅探 + 占位文本识别 + 自动重取。
      含真机实测到的 **GBK 被按 Big5 解码**这一形态（`mojibake:gbk-as-big5`）——
      这类乱码根因在源头，重刮救不回来，报告要说清形态并让用户提供正确原文
- [x] **保留本地时间轴**：外文单语歌词沿用用户文件里的时间轴与断句，只按相同时间戳插译文行
- [x] 内嵌歌词检测 + 提示（**清除能力**不做：要改写音频文件，风险高）
- [x] 结果面板：状态筛选、CSV 导出、逐曲预览
- [x] 回滚（按曲从 `.bak` 恢复）

**三端与分发**
- [x] Web UI（选目录 → 扫描 → 预览 → 执行 → 报告）+ SSE 进度
- [x] 桌面窗口（双击启动，起本地服务 + 原生窗口；无 pywebview 时退回浏览器）
- [x] CLI（`scan` / `run` / `report` / `config` / `token` / `serve` / `fnos`），带退出码
- [x] Docker 镜像 + 飞牛 NAS 部署文档

**飞牛歌词库（`fnlrc fnos`）**
- [x] 只读探测（两处路径、真机表名列名回显、关联自检）+ 差异计划
- [x] 原地回填：只换正文、保留 `lyric_id` → 歌单 / 收藏 / 播放历史 / 歌词偏移全不受影响
- [x] **给"一行歌词都没有"的歌新建歌词行**（`--allow-insert`，默认关）

### 待办

- [ ] **二轮补跑**：对 `no_lyrics` / `timeout` 自动重试（换关键词、用专辑名 / 罗马音）。
      清洗逻辑本身已实现（`library.base_title()` 剥 `_hires` / `(Short Size)` 等并参与匹配），
      缺的是调度
- [ ] 语言标签补全（写回 `language`，提升后续匹配与校验准确度）
- [ ] **多版本共存**：同一首歌保留多个歌词版本。真机实测过做法（`INSERT` 之后必须
      upsert `user_track_lyric_preference`，否则 `preferred` 停在旧行、用户看不到新版本），
      但收益不明确而风险实打实，所以暂不做
- [ ] provider 插件化（社区可加源：QQ 音乐 / 酷狗 / Musixmatch…）
- [ ] 人工翻译导入 / 导出
- [ ] macOS / Linux 桌面打包
- [ ] i18n（中 / 英）

## 四、"做完"的验收标准

每个版本都要**能独立用**，并且有可演示的验收：

**v0.1 · 能跑通全流程（桌面单 exe）** ✅
1. 双击 exe → 窗口出现（无控制台黑框），3 秒内可交互
2. 选一个含 500+ 首的库 → 扫描出正确统计（与人工核对误差 0）
3. 预览模式跑 20 首 → 生成的双语文件**全部通过飞牛规则校验**
4. 写入模式跑同样 20 首 → 原有 `.lrc` 都产生 `.bak`，新文件在飞牛里**确实显示双行**
5. 全程零配置（不填 key、不装模型）

**v0.2 · 覆盖率与可维护性** ✅
1. 报告页能按状态筛选、导出 CSV、逐曲预览
2. 回滚后库内文件与运行前**逐字节一致**
3. 任务中断后重启，历史任务与结果仍可查看

**v0.3 · 分发** ✅
1. `docker run` 一条命令在飞牛 NAS 上跑起来，直接读写 `/vol2/1000/音乐`
2. 新用户从下载到看到第一首双行歌词，**不超过 5 分钟**

**v1.0 · 可给别人用**（进行中）
1. 陌生人按 README 独立完成一次全库补完，无求助
2. 已知问题清单收敛到「第三方源覆盖」这类不可控项
3. 有 ≥3 个真实用户的库被成功处理过

## 五、项目层面的"Done"

1. **对用户**：一个不懂技术的人，5 分钟内让日语歌显示双行
2. **对库安全**：任何情况下都能一键回滚到运行前状态
3. **对覆盖率**：一库 500 首，最终「无歌词 + 可疑」占比 < 10%
4. **对维护性**：新增一个歌词源 = 新增一个文件，不改核心
